## 二、P0 核心安全保存机制（Windows openpyxl 异常防截断护栏）

### 1. 缺陷根因确诊
在 Windows 运行环境下，Python 的 `openpyxl.Workbook.save(path)` 实现内部采用直接以写模式打开目标文件流的方式打包 zip。当遭遇权限锁、系统沙盒拦截（如 WinError 5）或写入中途中断时，目标文件已被以 0 字节清空，随后写入残缺的 2.3KB 损坏文件（缺少 `[Content_Types].xml` 导致再也无法读取）。由于 `workbook/*.xlsx` 是项目的**唯一不可再生权威源**，该机制具有致命破坏性。

### 2. 解决方案：`safe_save_workbook`
在 `pipeline/common.py` 中实现了基于内存流校验与操作系统原子替换的安全保存函数：
1. **内存预封包**：先利用 `io.BytesIO()` 在内存中完成 Excel 序列化，确保写入逻辑无异常抛出。
2. **同盘临时文件落盘**：在目标文件所在父目录创建临时文件（`tempfile.NamedTemporaryFile(dir=target_dir, delete=False)`），确保后续替换处于同一磁盘分区。
3. **系统级原子替换**：调用 `os.replace(tmp_path, target_path)` 完成瞬时原子覆盖；若发生任何异常，自动清除临时文件，目标权威源绝不被触碰。
4. **全面替换调用点**：将 `pipeline/apply_sentence_edits.py`、`pipeline/relations.py` 及 `app/tools/overrides.py` 中的 `wb.save` 全面重定向至 `safe_save_workbook`。

## 三、P1 数据层段落落库与注文跳转闭环

### 1. 段落缺失根因确诊
历史单体包时代为了缩减 JSON 体积，`pipeline/annotate.py` 与 `annotate_places.py` 在末端过滤掉了没有实体命中的句子：
```python
# 历史遗留问题：过滤了没有实体命中的纯正文句子
sentences = [s for s in sentences if s.get("persons") or s.get("places")]
```
导致数据库仅收录了 96,453 句，丢失了 126,711 句正文（丢句率达 56.8%），引发：
1. 原文阅读器正文开洞，断断续续，无法作为严肃古籍阅读系统使用；
2. 304 处注文明细指向的段落根本未入库，用户点击注文跳转无反应或定位错位。

### 2. 段落连贯性重构方案
1. **保留全量句子流**：
   - 修改 `pipeline/annotate.py`：所有自然文本句子全量按原始段落与句序输出，无实体命中时填充 `persons: []`、`marks: []`。
   - 修改 `pipeline/annotate_places.py`：移除对纯文本句子的过滤，全量 223,164 句完整写入 `book-data.json`。
2. **纯注文段落空段锚定与回退守卫**：
   - 维基文库解析中，某些纯注文在 `build.py` 被切分为独立空段落（`sentences: []`，如 `sgz-11` 第 9 段）。
   - 修改 `pipeline/annotate_pei.py` 与 `pipeline/annotate_js_note.py`：新增 `last_text_pseq` 动态跟踪指针，当注文本段为空时，自动将其 `pseq` 锚定到它所依附的前一个正文段落。
   - 修改 `app/web/app.js`：在 `jumpToPara(pno)` 增加向前回溯安全兜底：
     ```javascript
     while (!node && cur > 1) {
         cur--;
         node = document.querySelector('.reader-p[data-pseq="' + cur + '"]');
     }
     ```
3. **长章节分页突破**：
   - 修改 `app/server/db.py` 与 `app/server/main.py`：将 `chapter_sentences` 默认 `limit` 从 500 提升至 5000。
   - 解决了包括《史记·十二诸侯年表》（`sj-014`，共 3,454 句）在内的 108 篇长章节被截断的问题。
