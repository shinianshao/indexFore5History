## 三、剩下的四块：方案与工作量

> 单位是人时（含写断言）。工作量是估算，按「后端改动 + 前端实现 + 断言」三段拆。

### 3.1 原文层跳段 —— 1h，风险低

纯前端。`/api/chapter/{cid}` 已经返回段落数据，缺的只是一个「跳到第 N 段」的入口。
**性价比最高的一块**，建议第一个做。

### 3.2 裴注区块 —— 3h，风险低

- 后端 1h：建 `pei_mentions` 表（2,829 行，从 `pei-data.json` 灌），
  `/api/person/{pid}` 附带 `pei: {n, chapters, byChapter, items}`。
- 前端 1.5h：`peiSection` 照静态版结构抄（按篇 Top 12 + 明细卡）。
- 断言 0.5h：**必须有一条断言守「裴注不进 mentionCount」**——这条红线一旦破，
  所有命中数都会悄悄变。

⚠️ 概念风险：裴注是**独立账本**，页面上的「合计」要像静态版那样标成【裴 N】，
不能和正文命中混在一个数里。

### 3.3 人物详情别名分组表 —— 3h（简化版 2h），风险低

静态版按 `kind` 分组、每片带 `×N` / 「未用」、hover 显示异写。
数据**已经在 book-data.json 里**（`aliasList` 含 `w / simp / n / kind / variants / byBook`），
只是没进库：

```
kind 分布：name 2240 / title 618 / generic 170 / other 891 / short 6
```

- 后端 1h：`aliases` 表加 `kind` / `variants` / `by_book` 三列（6,040 行）。
- 前端 1.5h：`aliasTable` + `placeAliasTable`。
- 断言 0.5h。

价值判断：这块**值得做**——「漢王 ×739」「未用」是用户判断
「这个词到底算不算他」的唯一依据，比多加一个索引页有用。

### 3.4 单书朝代分组 —— 2h（降级版 0.5h），风险中

静态版在单选断代史时，把人物索引拆成「本书记载时代」/「相对于本书的古人」两组。
数据也在（人物有 `eraRank`，书有 `eraRange`）：

```
有 eraRank 的人：2,071 / 2,240（缺 169）
eraRange：hs [8,10]  hhs [10,11]  sgz [11,12]  js [12,15]  sj 无（通史）
```

⚠️ 两个坑：
1. **史记是通史，`eraRange` 为 null** → 这个功能对史记完全无效（静态版也是这样）。
2. **169 人没有 eraRank** → 会被一律分到「古人」组，是错的但不显眼。

**我的建议：降级为一个小标记**（条目上加「前朝」二字），不做分组。
理由见 §五。

## 五、难以实现 / 特别耗费资源的地方

### 5.1 真正的结构性成本：两套前端

`web/` 48MB（含 34MB 的 app-data.js）+ `app/` 0.3MB，两边都有 `app.js` / `index.html`。
**每加一个功能理论上要改两处**。虽然 `web/` 已冻结，但 `run_all.sh` 里仍跑着
4 个针对静态版的 UI 测试（人物页 / 多书检索 / 地名层 / 样式表），
每次回归还要额外起一个 `http.server`。

这不是「难」，是**持续的税**。见 §六第 1 条。

### 5.2 pid 重命名：越往后越贵

676 个占位 pid + 17 组同名要合并。**改 pid 会同时牵动**：
`workbook/relations.xlsx`（99 条边）、`overrides.xlsx`、`sentence-edits.xlsx`、
`people.json`、以及所有引用 pid 的断言。

它不是「难点」（机械替换 + 全量重建 34s 就能验），
但它是**唯一一类「拖越久越贵」的活**——每多落一批关系、每多录一条 override，
要改的引用就多一批。**建议排在前端细节之前。**

### 5.3 重名合并是唯一无法自动化的

17 组同名（劉焉 3 人、陶謙/鄭弘/賈逵/王霸/曹節/張禹/劉隆 各 2 人……）
必须人工看原文拍板——项目规矩是「判不了勾未知，不要硬判」。
AI 只能做取证（归属分布 + 原文上下文 + 候选朝代），不能替人决定。

### 5.4 关系上量：建议明确画界线

当前 99 条边，其中 68 条置信度 0.4（无证据的推断）。
MEMORY 里记着：**「简介这条线已近抽干」——含关系词 70 条，已出边 59，剩 11**。

要上量只能从 96,336 句正文里抽。这是我最想劝退的一项：
没有标注数据、误判不可见（会画成实线误导人）、且规模没有天然上限。
**要么只做小范围试点（一个书、一种关系），要么明确不做。**

### 5.5 磁盘：133.6MB，单机无压力但有个坏味道

```
data/index 133.6（book-data.json 32.8 + index.db 55 + corpus 53.9...）
data/corpus 53.9    data/raw 28.1    data/dict 1.1
```

不算大。但 `annotate` 每一步都要把 **32.8MB 的 book-data.json 整体读进内存再整体写出**
（`annotate_places` 更是「就地修改」同一个文件）。当前可接受；
如果将来真要接新史书，这里会先出问题。已决定不接新书，所以不动。

## 六、讨价还价：我建议怎么改你的需求

### 第 1 条：别再给静态版交税 —— 请做一次明确决策

静态版已冻结，但它的 4 个 UI 测试还在每次回归里跑。
三个选项，我推荐 A：

- **A（推荐）**：静态版测试**保留但降频**——只留「样式表 `_ui_csscheck.js`」进日常回归，
  另外 3 个挪到 `--full`。理由：对齐完成后，静态版不再演进，
  天天为它跑 4 套测试是在给一个死掉的分支交税；但它毕竟是「对齐的参照物」，全删不安全。
- B：全部迁到 `app/web`（工作量大，且要重写断言里的取数方式）。
- C：维持现状（继续交税）。

### 第 2 条：「跟原来一样」不该 100% 照搬

静态版有些设计是**当年为了绕开「没有数据库」而做的妥协**，照搬就是开倒车：

| 静态版 | 新版 | 我的意见 |
|---|---|---|
| 一次性加载 32.8MB | 按需查库 | ✅ 新版更好，**不要**为了「一样」改回去 |
| 快捷词固定 Top N（不换书） | 换书跟着换 | ✅ 新版更好 |
| 数据全在前端，离线可用 | 需要跑服务 | ⚠️ 这是静态版**唯一真正的优势**，见第 6 条 |

反过来，新版独有的（关系图、FTS5 全文检索、句级编辑）是净增量，**不要砍**。

### 第 3 条：砍掉「晉書舊史注」的 UI 区块

它只有 **4 篇 / 69 个命中**。为它做一个和裴注同规格的区块（1.5h）是纯浪费。
**建议只留一行**「另有舊史注 N 處」（0.3h），效果几乎一样。

### 第 4 条：单书朝代分组 → 降级为小标记

拆成两组会让索引页**翻一倍长**，而它：
- 对史记完全无效（通史，无 eraRange）；
- 169 人缺 eraRank，会被误分到「古人」；
- 真实需求（「找本书记载的人」）用「按书计数 + 按篇数排序」已经基本满足。

**建议只加一个「前朝」标记**（0.5h），省下 1.5h。

### 第 5 条：pid / 同名合并要**插队**到前端细节之前

理由见 §5.2：它是唯一「越拖越贵」的活。
代价：前端那几块会晚一两天看到。收益：后面所有活都不用再回头改引用。

### 第 6 条：有一个我**不该替你决定**的取舍

「离线可用」——静态版 `web/index.html` 双击就能开，新版要跑 FastAPI。
这次对齐**没有解决这个问题**，而它直接决定「这些索引能不能发给别人用」。

- 想要离线分发 → 得做一个「导出静态快照」的步骤（从库里导出一份精简 JSON，估 4–6h）。
- 只在自己机器上查 → 不用管。

**这条请你定**，我不擅自排进计划。

## 八、一句话总结

数据规模不大、重建只要 34 秒、回归只要 4 分钟——**这个项目的本钱是「改得起」**。
真正的成本不在任何单个功能，而在两处**结构性**的地方：
**两套前端长期并存**（持续税）和 **pid 迟迟不改**（越拖越贵）。
前端那几块加起来不过 6–7 小时，随时可以做；
但 pid 和同名合并再拖下去，将来每一次改动都要多付一笔。
