## 二、审查意见（P0 / P1 / P2）

### P0 · 动工前必须解决

| # | 问题 | 后果 | 建议 |
|---|---|---|---|
| 1 | **落点错了**：关系在 index.db（可删重建的派生库），且无灌入步骤 | 下次重建全丢，静默 | 权威源 `workbook/relations.xlsx`，建库后由脚本灌回 |
| 2 | 无 `status`、无稳定业务主键（`id` 每次重建重排） | 判错只能物理删；外部引用全漂 | 加 `rel_id`（稳定串）+ `status`(active/dead/superseded) |
| 3 | `evidence_uid` 没处理**一对多**与**句子生命周期** | 一句支持多条关系 → 图上重复边；句子被弃用后仍被引用 → **假证据** | 见 §三的 V1 取舍 |
| 4 | `evidence_text` 与 uid 谁权威，文档说反了 | 与红线②（句子以 uid 为准）冲突 | **以 uid 指向的现句为准**，快照只是展示缓存；不一致则报警 |
| 5 | `direction` 语义未定义 | `(a,父,b)` 与 `(b,子,a)` 双写成最常见脏数据 | 只存**规范边** + `symmetric` 布尔；反向由代码 `REL_INVERSE` 派生 |
| 6 | **契约是"看起来有接口其实跑不通"** | 灌数据必返工 | `db.person_relations` 返回扁平行，而 `renderGraph` 契约是 `{nodes,edges}`；前端占位卡片**根本不读** `d.relations`；端点无 degree/type/book/王朝/置信度参数 |

### P1 · 动工中解决

7. **缺时间性与同名异人锚点**：同一人不同时期身份不同（先部屬后主君）；自 summary 抽 pid 必撞 18 组同名异人 → 边要存 `surface_a/surface_b`（原文用字）+ `book` + `era`。
8. **枚举**：`rel` 定死在代码常量里（含定义/正反例/反义词），`rel_type` 由 rel **派生、禁止手填**；枚举外先记 `other`+note，攒批再扩。
9. **confidence 由 `source` 派生、不手填**（手填会出现"标 manual 实为猜"，无法断言）。AI 档缺值需补齐。断言：`manual-guess ⇒ ≤0.4`、`auto-summary ⇒ evidence_uid 非空`。
10. **边上冗余 `book`**：否则按书过滤要 join mentions/sentences，代价高且语义含糊。
11. **pid 重命名应排在 P6 之前**（关系以 pid 为外键，先灌后改要迁上万行）。

### P2 · 可延后

12. 规模：2,240 节点 / 上万边，一、二度邻居在已有 `ix_rel_a/ix_rel_b` 上毫秒级；三度用递归 CTE 够，**不必物化**。
13. 断言：现有 113 条无一覆盖 relations，需补（两端 pid 存在 / rel 在枚举内 / rel_type 与 rel 一致 / confidence↔source 匹配 / evidence_uid 有效 / 无自环 / 无反向双写）。

## 三、我方判断（哪些采纳、哪些改）

**P0 六项全部采纳**——尤其第 6 条我自己写的契约确实有错觉（当时以为「接口定死了就不用改」，
实际返回结构与前端输入对不上）。

两处我做**V1 取舍**，与审查建议不完全一致，理由写在这里：

| 项 | 审查建议 | V1 做法 | 理由 |
|---|---|---|---|
| 证据一对多 | 主表一条边 + `relation_evidence` 子表 | **先只用主表 `evidence_uid`/`evidence_text`**，加唯一约束 `(a,b,rel,evidence_uid)` 防重复 | 从 summary 抽的关系，每对每种关系通常只有一处证据。子表是将来必然要的，但把主表两列搬进子表的迁移成本很低，不值得现在付 |
| 反向边 | 只存规范边 + 代码派生 | 同左，但 **`REL_INVERSE` 映射表先只覆盖 kinship**，political/social 的反义大多不成对 | 政治/社会关系（政敵、友）本来就是对称的，不需要反义表 |

另外补一条项目自己的规矩：**证据快照 `evidence_text` 与 `overrides.xlsx` 同规矩——
只在录入那一刻写，重建绝不刷新**（否则又是一次「脚本冲掉人的审定」）。

## 四、动工前要定死的几件事（P6-0）

### 4.1 表结构（`relations`，仍是派生的，权威源在 xlsx）

```
rel_id        TEXT UNIQUE     md5(person_a|person_b|rel|book|era)  ← 稳定业务主键
person_a / person_b   TEXT
surface_a / surface_b TEXT    原文用字（同名异人消歧 + 复核「这条边指哪个人」）
rel           TEXT            规范词表，定死在代码常量
rel_type      TEXT            由 rel 派生（kinship/political/social/other），代码填
symmetric     INTEGER         1=对称（兄弟/友/政敵/同僚）；0=有向
era / book    TEXT            可空，用于时间性与按书过滤
evidence_uid  TEXT            可空
evidence_text TEXT            录入那一刻的快照，只读缓存
confidence    REAL            由 source 派生，不手填
source        TEXT            manual / ai / auto-summary / manual-guess
status        TEXT            active / dead / superseded
note / created_at
```

索引：已有 `ix_rel_a/ix_rel_b/ix_rel_type` + 新增 `UNIQUE(rel_id)`、`(person_a,person_b)`、`evidence_uid`（改句子时反查受影响的边）。

### 4.2 `workbook/relations.xlsx` 列（人写 / AI 落盘，管线只读）

`rel_id | person_a | 原文用字a | person_b | 原文用字b | 关系(rel) | 对称 | 时代 | 书 |
证据uid | 证据原文 | 来源(source) | 状态 | 备注 | 录入时间`

`rel_type` 与 `confidence` **不进表**（由代码派生），与 `overrides.xlsx` 同一套规矩：
会由脚本填的列只在录入那一刻写，重建绝不刷新。

### 4.3 契约（P6-1，灌数据前先定型）

```
GET /api/person/{pid}/relations?degree=1|2&type=kinship&book=hhs&min_conf=0.6&limit=200
→ { nodes: [{id, name, dynasty, degree}],
    edges: [{source, target, rel, rel_type, confidence, source, symmetric, evidence_uid}] }
```

前端 `renderGraph(adjacency, options)` 的输入就是 `{nodes, edges}`；
`renderPerson` 里那张硬编码的"關係圖 預留"卡片要改成**有则画、无则显示 0 条**。

### 4.4 动工顺序

## 六、修复时新发现的两件事（补记）

1. **边上的 `source` 撞键**：图标准里「起点」叫 `source`，而项目字段「关系来源」
   也叫 `source`。两个同名键写进同一个 dict，后者无声覆盖前者——
   端点一度返回 `"source": "manual"`（起点变成了来源名）。
   改法：**起点/终点用 `source`/`target`，关系来源改叫 `origin`**。
2. **断言会假绿**：`verify_p3` 里跑 `rebuild` 时若库被别的服务占着，rebuild 会失败，
   但旧库还在、关系也还在——此时直接比对「重建后关系仍在」是一条**假绿**。
   改法：**先断言 rebuild 退出码为 0，再比对数据**。
   （这正是审查 P2-13 说的「故意注入错误必须变红」的同类问题——
   断言不仅要能红，还要保证它比的确实是刚跑出来的结果。）
