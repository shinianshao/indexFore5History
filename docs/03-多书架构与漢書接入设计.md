## 一、需求拆解

| 用户原话 | 落到系统上的含义 |
|---|---|
| 增加书籍后，针对每本书建立独立的检索条目列表 | 人物索引 / 地名索引 / 篇目一览 **三张列表都要按书隔离**；每本书一套条目，互不串味 |
| 检索可以是在一本书内进行 | 检索作用域 = 单本书；命中句、称谓表、篇目都只来自该书 |
| 再设置一个多书检索，可以同时选几本书给出所有的检索结果 | 作用域 = 书集合；同一实体在所选各书的命中**汇总**展示（按书分组 + 总计） |

关键推论：**实体（人物/地名）必须跨书唯一，命中必须按书分开。**
用户勾选《史记》+《汉书》搜「刘邦」，看到的是**一个**刘邦条目，下面分列两书的命中——
而不是「刘邦（史记）」「刘邦（汉书）」两条让人自己合并。这一条决定了下面所有的设计。

### 2.3 《汉书》语料实测（维基文库）

- 主页面 `漢書` 存在；子页面 131 个。
- **19 个是重定向**：`卷001上`/`卷001下` → `卷001`，`卷027中之上` → `卷027`，……
  → 抓取必须**解析重定向并去重**，否则同一卷抓三遍、正文重复。
- **4 个非卷页**：`景祐刊本校語`、`漢書敘例`、`韓彭英盧吳傳`、`髙惠髙后文功臣表`
  → 不入库（校语/叙例是编者文字；后两个是别本转录，与正卷重复）。
- **规范卷页 108 个**，slug 形态不规则：

  ```
  卷001 … 卷015, 卷015b, 卷017 … 卷027, 卷027下之上, … 卷064上/下,
  卷094上/下, 卷096上/下, 卷097上/下, 卷099上/中/下, 卷100上/下
  ```

- **缺 `卷016`**（wikisource 无此页）。汉书本为 120 卷，此处实得 108。
- 网络不稳定：实测出现 `Tunnel connection failed: 502`，需退避重试 + 断点续抓。

## 三、核心设计决策

### 决策 1：实体跨书唯一，命中按书分开 ★

```
实体（全局唯一）                     出现（按书）
─────────────────────               ─────────────────────────
p_liubang  劉邦 / aliases / summary  ├ sj: {mentionCount:938, chapters:59, aliasList:[…]}
                                     └ hs: {mentionCount:?,  chapters:?,  aliasList:[…]}
```

- 顶层 `mentionCount / mentionChapterCount` **保留不动**，语义变为「**当前作用域**的合计」：
  单书模式 = 该书的值；多书模式 = 选中各书之和。
  → 这是刻意的：`verify.py` 20 条断言、`_ui_sweep.js` 1047 条对账、`_ui_test*.js`
  100 条全部读这两个字段。若改成只有 `byBook`，回归面会瞬间放大到不可控。
- 新增 `byBook: {code: {mentionCount, chapterCount, aliasList, chapters}}`，
  **只增不改**：单书模式读 `byBook[code]`，多书模式把选中各书相加、章节合并去重。

**为什么不做「每书一套实体表」**：那会让多书检索冒出两个刘邦，正是用户要避免的。
**为什么不做「只保留全局聚合值」**：那做不出「每本书独立的条目列表」。
代价：`byBook` 让数据结构变复杂，但换来两种检索模式都自然，且存量断言零改动。

**多书时的排序与展示**（v1 未定义，补）：
- 索引列表按**作用域内合计处数**降序——多书下刘邦仍是第一条，不会因分书而掉位。
- 点进人物页后**按书分组**：每组给「书名 · N 处（M 句）」，再给总计；
  篇目卡片带书标识（前缀书名），避免两书同名牌（如两书都有〈陳勝項籍傳〉/〈陳涉世家〉）混淆。

### 决策 2：卷标识用 slug，不强行转 int

`chapterId = "{code}-{slug}"`，slug 直接取维基文库卷后缀去「卷」字：
`hs-001`、`hs-015b`、`hs-027下之上`、`hs-099中`、`hs-100下`。

同时保留两个字段便于展示与排序：
- `volume`: 整数序号（`015b` → 15），用于「卷 N」展示
- `slug`: 原文，用于稳定 id 与抓取
- `chapter_sort_key` 改为 `(bookIndex, volume, subOrdinal)`，
  `subOrdinal`: 无后缀 0 / 上 1 / 中 2 / 下 3 / 之上·之下 1·3 / `b` 9。

> 史记可保持 `sj-001` 不变（slug = 三位数字），**零迁移成本**。

### 决策 3：管线保持单一产物，前端按书拆分加载

- 管线仍产出**单一** `data/index/book-data.json`（含全部书）——
  体检工具（`verify.py` / `resolve.py` / `_ui_sweep.js`）无需大改，对账方便。
- 新增 `export_web.py` 把它**拆成** `web/data/app-data-{code}.js` + `corpus-data-{code}.js`。
- 前端常驻只加载 `web/data/books.js`（注册表，几 KB），
  **切到哪本书 / 勾了哪几本书，才按需注入对应 js**。
  → 避免把 13 MB 一次性塞进页面。

### 决策 4：书注册表驱动，新增书不改代码

新增 `data/dict/books.json`：

```json
{
  "sj": {"code":"sj","name":"史記","order":0,"volumesFile":"volumes/sj.json",
         "source":{"site":"wikisource","titlePrefix":"史記/卷"}},
  "hs": {"code":"hs","name":"漢書","order":1,"volumesFile":"volumes/hs.json",
         "source":{"site":"wikisource","titlePrefix":"漢書/卷"}}
}
```

`build.py` / `fetch.py` / `annotate*.py` 一律遍历注册表，不再写死书名。
`python run_pipeline.py --book hs` 可只跑汉书（史记产物不动）。

### 5.1 阶段 0 的硬闸门：史记产物零回归

任何多书改造**先过这一关**再往下走：

```
跑改造前 → _snapshot_counts.py（存 before）
跑改造后 → _snapshot_counts.py --mode diff
要求：766 人物 + 281 地名 逐 id 的 mentionCount / mentionChapterCount 全部不变，
```

### 5.2 阶段 3 详解：汉书篇主表（本工程最大的人工工作量）

「整篇讲述」的判据是**篇名即主人公**，因此每卷都要一份 slug → 篇名 → 主人公 的映射。
汉书 100 篇的构成：**12 紀 + 8 表 + 10 志 + 70 傳**（与史记同构，可复用同一判据）。

推导策略（先自动、后人工，与人物层「挖掘器只召回、精确性由人负责」同一规矩）：

1. **自动**：维基文库卷页首行即篇名（实测 `漢書/卷001` 正文首见「高帝紀第一」）→ 抓取时顺带存篇名。
2. **映射**：`高帝紀` → 刘邦；`陳勝項籍傳` → 陳勝 + 項籍。与史记 `CHAPTER_OWNERS` 同一写法。
3. **人工审**：表（8 表）、志（10 志）无主人公，与史记一样留空（`CHAPTER_OWNERS[13..22] = []`）。
4. 汉书独有人物（王莽、班固、赵飞燕、霍光、苏武…）并入全局 `PERSONS`，id 全局唯一。

风险：108 卷的人工审读是本工程**最耗时**的一步，需分批推进；
可先只做 12 紀 + 主要列傳，保证核心可用，再补齐。

### 5.3 阶段 5/6：存量测试必须同步改，不能绕过

拆分 `web/app-data.js` 会动到测试的加载路径——`_ui_test.js` / `_ui_test_places.js` /
`_ui_sweep.js` 都是起 http 服务读 `web/` 再注入 DOM 的。因此：

- 阶段 5 起，三套 UI 测试的**加载方式**要跟着改（改为加载 `books.js` + 按书 js）。
- 阶段 6 的回归必须**两套都跑**：
  1. **史记单独作用域**：原有 51 + 49 + 1047 条断言**一条不许少、不许改期望值**
     （除了确实该变的加载方式）；
  2. **多书作用域**：新增断言——书选择器存在、单书检索只出该书结果、
     多书检索出两书结果且处数为合计。
- `verify.py --check` 的 20 条在阶段 0–4 保持全过；阶段 5 后如因 `byBook`
  改变字段位置需调整，必须**逐条确认是字段迁移而非行为变化**。

## 九、《汉书·地理志》郡县地名补录

在汉书人物/篇目接入完成后，地名层也按同一套「书作用域」扩展，新增《汉书·地理志》所载郡县名。

### 9.1 提取与筛选口径

- **来源**：`data/corpus/hs-028.json`《漢書·地理志》中「縣N：A，B，C。」清单。
- **原始规模**：103 条清单 / 1571 个去重县名（与史载「縣邑千三百一十四」大致吻合，差额来自重复县名）。
- **排除规则**（逐条有记录）：
  1. 已被现有地名词典收录 → 跳过；
  2. **单字县名全部跳过**（213 个）：于/京/代/平/成/文/張/高/黃… 等单字在全书里噪声极高，收益/风险比差；
  3. 与人物专名/别名完全重合 → 跳过；
  4. 被现有人物标记覆盖 ≥35% 且出现 ≥3 次 → 疑似人名/爵号，跳过（如 安國／韩安国、充國／赵充国、臨江／临江王、辟陽／辟阳侯 等）；
  5. 年号/常用词 → 跳过（建平、長子、萬年 等）。
- **本次补录**：**1175 条**（≥2 字），全部只匹配《汉书》（`books: ["hs"]`），保护《史记》侧零回归。

### 9.2 技术处理
