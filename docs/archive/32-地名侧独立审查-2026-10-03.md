- **位置**：`app/tools/build_index_db.py:411-430`（寫法集合 `forms` 來自 book-data 的 `aliases`）

  1. 灌庫時把**語料裡出現過但 aliases 沒登的寫法**也併進 `forms`（標一個 `from_surface=1` 或直接排在 aliases 之後），做到「權威源登的 + 語料真的用的」聯集。這符合「規則進程式碼、資料進表格」——不動 `workbook`，只在建庫這一步做聯集。

  3. 明確記為已知限制，寫進 `docs/31`，說明「洛水 598 處中 499 處可檢索，餘下 99 處用的是『雒』這個寫法，權威源未登」。

#### P1-2　`export_static.py --check` 對 `plalias` / `plbook` 兩塊完全無感

- **位置**：`app/tools/export_static.py:377-380`（`counts` 字典）、`619-625`（`check` 比較邏輯）
- **症狀**：`counts` 裡只有 `place_mentions` 一個地名側計數，**沒有 `plalias` / `plbook`**。實測三個場景的判定：
  ```
  場景1 舊快照缺 place_mentions 鍵       → ['place_mentions(缺鍵·快照早於地名命中)']  ✅ 抓得到
  場景2 快照裡 plalias/plbook 整塊丟了    → 報同步（= 漏了也不報）                    ❌
  場景3 plalias 內容為空 {}              → 報同步（= 漏了也不報）                    ❌
  ```
  也就是說：若下次有人改 `BIG` 元組時把 `plalias` 漏掉、或 `_plalias()` 寫壞返回空對象，`--check` **會報「快照與庫同步」**，而離線版地名實際是「能檢索到正名、但輸簡體零命中」的半死狀態。
- **為什麼會這樣**：`check` 的鍵集來自 `new`（庫側計算），而 `plalias`/`plbook` 這兩個鍵在 `counts` 裡不存在，就永遠不在比較範圍內。`place_mentions` 有專屬的缺鍵檢查（625 行），但那個檢查只覆蓋它自己。
- **建議改法**：
  ```python
  # build() 的 counts 裡加兩條
  "plalias": sum(len(v) for v in plalias.values()),
  "place_alias_rows": <SELECT COUNT(*) FROM place_aliases>,
  ```
  然後把 625 行的缺鍵檢查從「只查 `place_mentions`」改成「查這三個鍵」。`place_books` 已有對應的 `place_mentions` 計數守著，`plbook` 可以不單獨加。

#### P1-3　`place_aliases` 無主鍵，`INSERT OR REPLACE` 退化成 `INSERT`

- **位置**：`app/tools/build_index_db.py:170-176`（建表）、`431-433`（寫入）
- **症狀**：`CREATE TABLE` 沒有 `PRIMARY KEY` 也沒有 `UNIQUE`，所以 `INSERT OR REPLACE` 裡的 `REPLACE` **永遠不生效**，退化成純 `INSERT`（追加）。同一份 book-data 灌兩次，行數翻倍。
- **為什麼會這樣**：這是 SQLite 的語義——`REPLACE` 只在主鍵或唯一約束衝突時刪除舊行。沒有約束就沒有「衝突」，於是每次都是插入。
- **影響評估**：**目前無實際危害**，因為 `main()` 在 288-291 行會先 `os.remove(DB + suffix)` 把整個庫刪掉重建（註釋也說明了「否則 mentions/aliases 是追加寫入，重跑一次就翻倍」）。而 `person_aliases`（112 行）同樣沒有約束、同樣用 `INSERT OR REPLACE`——**這是既有寫法，不是本次新增的違規**。
- **建議改法**（可選，防禦性）：
  ```sql
  CREATE TABLE IF NOT EXISTS place_aliases (
    place_id TEXT, seq INTEGER, w TEXT, n INTEGER, by_book TEXT,
    PRIMARY KEY (place_id, seq)
  );
  ```
  加了主鍵後 `INSERT OR REPLACE` 才是作者以為的那個語義。若怕動 `person_aliases` 引起意外，可只改地名牌（但兩張表不一致會更迷惑，建議一起改或都別改）。

#### P2-2　`search_places` 未轉義 SQL LIKE 通配符

- **位置**：`app/server/db.py:727`
- **症狀**：`like = "%{}%".format(q)` 未轉義 `%` 與 `_`。實測：
  ```
  search_places('%') → 30 條（秦/楚/齊…），253ms
  search_places('_') → 30 條，同上，257ms
  ```
  使用者輸一個 `%` 就會拿到「按命中數最多的 30 個地名」——不是他要的結果，而且 253ms 是正常檢索（4ms）的 60 倍。
- **影響**：人物側 `search_persons` 需另查（本次未逐行核對，見 §五）。若同樣未轉義，則是既有問題而非本次新增。
- **建議改法**：`like = "%" + q.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_") + "%"`，並在 SQL 裡加 `ESCAPE '\'`。

### 兩處與報告建議不同的地方

1. **P1-3 用 `PRIMARY KEY (place_id, w)` 而不是 `(place_id, seq)`**。
   `seq` 只是顯示順序，重建時會變，把它放進主鍵等於「順序變了就算另一行」→
   `REPLACE` 仍可能插重複。寫法本身才是身份。
2. **P1-1 選「合併」而不是「記為已知限制」**。理由：缺口不是罕見異體，而是
   **語料裡實際用過的寫法**（`河閒` 96 處 / `雒` 89 處 / `關内` 41 處），
   記為限制等於接受「用戶按原文寫法搜不到」的狀態。合併後
   `place_aliases` 2464 → **2525** 條，`Σ n == COUNT(place_mentions)` 對全部 1575 個地名成立。

### 對 §六 第 5 點的答覆：地名命中句不給「標錯」按鈕，是**遺漏**，不是設計

`renderPlace`（`app.js:641-`）只渲染了 `data-chapter` / `data-uid`，
沒有渲染人物側那三個定位字段（`data-s` / `data-e` / `data-surface`），
所以人物側 `app.js:598` 那個 `(!OFF && m.s != null && m.e != null)` 的按鈕條件
在地名頁根本沒機會成立。`app.js:627` 的註釋列舉了三項「地名側沒有的」，
確實漏了這一项。

**但這次不補**，理由是它屬於用戶已明確擱置的范圍（`docs/31` §四 P8-b
「地名標錯入口」待設計），且**必須先設計誤標判據**——地名的「錯」與人物的「錯」
不是一回事：一個 `surface` 可能正當地指向多個地名（`雒` → 洛水 / 洛陽），
「改歸」的目標欄位該填什麼需要先想清楚。已記入 `docs/31` 待辦。
