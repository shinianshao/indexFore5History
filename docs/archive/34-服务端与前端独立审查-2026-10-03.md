## 一、結論

**不能合併。必須先修 P0-1 與 P0-2 兩條，並把 P1-1 記為已知限制或修掉。**

與上一輪（docs/32）不同，這一輪的結論不是「功能對、斷言缺」，而是**功能本身就有三處壞的**，
而且**其中兩處正好落在這個項目的核心賣點上**（命中標色、聯機／離線一致）：

- **P0-1 命中標色標錯位置**：全庫 8,319 處標到了錯的字（人物 1,736 / 66,513 = 2.6%，
  地名 6,583 / 115,615 = 5.7%）。資料裡明明有 `s`／`e` 兩個欄位，前端卻用 `indexOf` 找第一個出現處。
  這不是樣式問題，是**標錯字**——使用者讀的是史記原文，標紅的卻是另一處同樣的字。
- **P0-2 注文區塊的「讀全篇 ›」與明細行是死按鈕**：`.open-full` 與 `.pei-line` 帶著
  `data-chapter` 渲染出來，但 `app.js` 的點擊分派**沒有任何一條分支處理它們**。
  實測點下去原文層不開，而同一頁的 `.sent` 命中行點下去正常開——**兩條相似路徑只接了一條**。
  而斷言寫的是「裴注區塊有篇級分布（**讀全篇可點**）」，實際上只斷了 `.length > 0`：
  **「有沒有」被當成了「對不對」**，這正是派工單點名的那類坑。
- **P0-3 聯機與離線的命中數口徑相反**：人物頁正文命中數，聯機是 200（`limit` 上限），
  離線是全量（曹操 1823、劉邦 2064）。而搜索結果卡片上寫的是全量。**同一個人，
  搜索卡說 1823 處、人物頁說 200 處**，兩塊數字在同一個介面上自相矛盾。
  這個分歧是「刻意」的（`export_static.py` 註釋寫了），但**界面沒有任何地方提示**，
  也沒有任何斷言守著它。

**測試的判別力比預期弱得多。** 15 組注入裡有 6 組「注入後全套仍然全綠」，
其中包括「把命中標色整個關掉」「把聯機注文區塊整個刪掉」「`/api/stats` 直接 500」。
換句話說，**這個項目的測試對「功能消失」這類壞基本不敏感**——它斷的多是「形狀對」，
而形狀在功能消失時往往不變。

#### P0-1　命中標色標到了錯的字（2.6% / 5.7%），且無任何斷言

- **位置**：`app/web/app.js:259-268`（`markSentence`）
- **症狀**（實測，`pipeline/_scratch/quant_mark.js` + 直接查 SQLite）：

  | 表 | 總命中 | `indexOf` 定位與 `s` 不符 | 比例 |
  |---|---:|---:|---:|
  | `mentions` | 66,513 | 1,736 | 2.6% |
  | `place_mentions` | 115,615 | 6,583 | 5.7% |

  實例（`uid=22da2f65f243`，人物頁 `p_liubang` 的第 2 條命中）：

  ```
  原文：或曰，樊噲常持鐵楯，聞項羽有意殺漢王，噲裂裳以裹楯，冠之入軍門，立漢王旁，視項羽。
  「漢王」在偏移 [16, 33] 兩處出現
  這條命中的真實 s = 33
  markSentence 標在第 16 字處   ← 標了「聞項羽有意殺漢王」那個「漢王」
  ```

  地名側同類：`surface=長安, s=19` 被標在偏移 1；`s=30` 被標在 8。
  短地名（「江」「河」）與疊字地名（長安）最容易被重複寫，所以地名側比例明顯更高。
- **根因**：`markSentence(text, surface, tier)` 的簽名**沒有收 `s`／`e`**，
  只用 `String(text).indexOf(surface)` 找第一個出現處。而呼叫方
  `app/web/app.js:593`（人物）與 `:680`（地名）手上**明明有 `m.s`**。
- **最小復現**：
  ```bash
  # 進曹操人物頁（拼音 / 或直接跑探針）
  # 找任意一句含兩個「漢王」的命中，看 <mark> 的位置
  node -e "/* 打 /api/person/p_liubang，取 mentions[1]，比 m.s 與 text.indexOf(surface) */"
  ```
- **斷言狀態**：**零**。`grep -n "markSentence\|<mark" pipeline/_ui_test*.js app/tools/verify_p3.py`
  → **無任何命中**。兩套 UI 測試共 148 條斷言，沒有一條看 `mark`。
  注入實驗 1（把 `<mark>` 換成 `<span class="nomark">`）→ **240+ 條斷言全綠**。
- **建議改法**：`markSentence` 加 `s` 參數，用 `text.slice(0, s) + <mark>surface</mark> + text.slice(s + surface.length)`；
  呼叫方傳 `m.s`；順帶處理 `s == null` 的退化情形（回退到 `indexOf`）。
  補一條斷言：**取一句內同字兩次的命中，斷 `<mark>` 前的字數 == `m.s`**（不要斷「有 `<mark>`」）。

#### P0-2　注文區塊的「讀全篇 ›」與明細行是死按鈕

- **位置**：`app/web/app.js:354`（渲染 `.open-full`）、`:368-370`（渲染 `.pei-line`）
  vs `app/web/app.js:1658-1743`（點擊分派，**無對應分支**）
- **症狀**（實測，jsdom 打真服務，`pipeline/_scratch/probe_openfull.js`）：

  ```
  注文 .open-full 存在: true  <b class="open-full" data-chapter="sgz-01">讀全篇 ›</b>
  注文 .pei-line  存在: true  <div class="pei-line" data-chapter="sgz-01" data-pseq="1" …>
  原文层当前 on: false
  点「讀全篇 ›」…      → 原文层打开了吗: false   ← 点了没反应
  点裴注明细行…        → 原文层打开了吗: false   ← 点了没反应
  对照组：点 .sent[data-chapter]（人物命中行） → 原文层打开了吗: true
  ```
- **根因**：`out.addEventListener("click", …)` 裡依序匹配
  `.item[data-place]` → `.row[data-place]` → `.item[data-name]` → `.chap-row[data-chapter]`
  → `.sort-toggle` → `.row[data-pid]` → `button[data-act=ovrebuild]` → `button[data-act]`
  → `.fixbox` → `.knob[data-k]` → `.rel-ev[data-uid]` → `.rel-node[data-pid]`
  → `.rel-edge` → `.rel-row[data-pid]` → `.sent[data-chapter]`。
  **`.open-full` 與 `.pei-line` 兩者都不在其中**，事件冒泡到最後什麼也沒做。
  `.pei-line` 還渲染了 `data-pseq`（段號），說明**原本打算跳到指定段**——連出口都沒接。
- **斷言狀態**：`pipeline/_ui_test_offline.js:484-488` 寫了兩條斷言：
  ```javascript
  ok("裴注區塊有篇級分布（讀全篇可點）",
     out.querySelectorAll(".open-full[data-chapter]").length > 0, …)
  ok("裴注明細行可點（能跳原文）",
     out.querySelectorAll(".pei-line[data-chapter]").length > 0, …)
  ```
  斷言**文字說「可點」，實際只斷「有」**。這是本輪最典型的「有沒有 ≠ 對不對」。
  而聯機側 `_ui_test_index.js` 連注文區塊都沒測（`grep -c "open-full\|note-sum"` → **0**）。
- **最小復現**：`PORT=8811 … python app/server/main.py` 然後開 `/#/person/p_caocao`，
  捲到「三國志裴松之注明細」，點任一「讀全篇 ›」——頁面不動。
- **建議改法**：在 `.sent[data-chapter]` 那條**之前**插兩條分支：
  ```javascript
  var of = ev.target.closest ? ev.target.closest(".open-full[data-chapter]") : null;
  if (of) { openChapter(of.getAttribute("data-chapter"), null).catch(showErr); return; }
  var pl = ev.target.closest ? ev.target.closest(".pei-line[data-chapter]") : null;
  if (pl) { openChapter(pl.getAttribute("data-chapter"), null,
                        null, pl.getAttribute("data-pseq")).catch(showErr); return; }
  ```
  並把 `openChapter` 的第四個參數接上（`jumpToPara` 已存在，可直接用）。
  斷言改成**真的點它**：點完斷 `reader.classList.contains("on")` 為真
  且 `readerTitle` 含該篇名——`pipeline/_ui_test.js:218-229`（靜態版）**已經是這個寫法**，
  諷刺的是新版把它退化成了「有元素」。

#### P0-3　聯機／離線的人物頁命中數口徑相反，且沒有任何提示

- **位置**：`app/server/main.py:186`（`limit: int = Query(200)`）＋ `app/tools/export_static.py`
  的「不截斷」刻意設計（註釋 `:19-25`）
- **症狀**（實測，`:200` 與 `mentions.length` 直接對比）：

  | 人物 | 搜索卡顯示 | 聯機人物頁 | 離線人物頁 | 搜索卡 vs 聯機人物頁 |
  |---|---:|---:|---:|---|
  | 曹操 `p_caocao` | 1,823 | 200 | 1,823 | ✗ 自相矛盾 |
  | 劉邦 `p_liubang` | 2,064 | 200 | 2,064 | ✗ |

  人物頁頂部的「正文命中 **200** 處　＋　注文另計【裴726】」——
  **200 是假的**（真值 1,823），而且它緊挨著「【裴726】」這個真數字，**用戶會以為
  「正文 200 + 裴注 726 = 926 處」**，實際是 1,823 + 726。
  這與 docs/29 §六-3「兩本帳分清」的初衷正好相反：分清了，但正文那一本帳的數字本身是錯的。
- **根因**：`person_payload` 把 `mentions` 截到 200，而 `notesSection(pid, notes, (d.mentions||[]).length)`
  （`app/web/app.js:609`）**把這個被截斷的長度當成「正文命中數」顯示**。
  數字存在，但**它是「本次載入了多少條」而不是「有多少處」**。
  搜索卡的 `n`（`search_persons` 的 `COUNT(*)`）與索引頁的 `n`（`list_persons` 的 `st["nAll"]`）
  **都是全量**——所以是**人物頁一處與其他兩處不一致**。
- **連帶影響（實測）**：
  - **原文層的段數**：108 篇聲明句數 > 500 的篇目，聯機 `limit=500` 截斷。

    `hs-027` 聲明 2,613 句，聯機 **500**，離線 **1,267**。
  - **「只看相關段落」的篩選口徑隨之不同**：`hhs-113` 聯機 453 段 / 離線 471 段；
    `hs-001` 聯機 70 段 / 離線 108 段。`JUMP_MIN=40` 的顯示與否在兩邊可能不同。
  - `renderParagraphs` 裡的「續接標記」`open` 計數在**被截斷的尾部**會停在半開狀態，
    跨屏閱讀時對話引號會錯位。
- **斷言狀態**：**零**。`grep -n "mentions.length\|正文命中" pipeline/_ui_test*.js` 無命中。
  斷言只看「有渲染出命中行」「分篇標題有篇名」——**200 條和 1,823 條都能通過**。
- **建議改法**（三選一，按作者口味）：
  1. **最小改**：人物頁的「正文命中 N 處」不要用 `mentions.length`，
     改用 `profile.aliasList` 裡 `kind==="name"` 的 `n`（那是 `build_alias_list` 算的全量），
     或在 payload 裡加一個 `mentionTotal`（`SELECT COUNT(*)`，一條 SQL 而已）。
  2. **誠實標註**：滿 200 條時在人物頁頂部掛一行「（只載入前 200 處，全書共 1,823 處）」。
  3. **一致性優先**：把聯機的 `limit` 提到 2,000（`MAX_LIMIT` 已是 500，需一併調），
     讓兩邊口徑相同——但這會讓 `/api/person` 回傳體變大，需評估。

  順帶請把「原文層的 500 句上限」在界面上也說一句，否則讀《十二諸侯年表》時
  「一共 3,454 句」的篇目只顯示前 500 句，用戶無從判斷這是篇目的全部還是片段。

#### P1-1　`hitParas()` 的「沒數據 → 不篩」註釋與代碼相反，會白屏

- **位置**：`app/web/app.js:827-836`
- **症狀**（實測，直接調函數）：
  ```
  uids=null  → hitParas = {}   渲染段落数 = 0   （註釋說「宁可全顯示」，應為 3）
  uids={u2} → hitParas = {"2":1}  渲染段落数 = 1   ✓
  uids={}   → hitParas = {}   渲染段落数 = 0
  ```
- **根因**：`if (!uids) return;` 寫在 `forEach` 的**回調體內**，
  `return` 只跳出**當前這一句**，外層 `forEach` 繼續跑，於是 `out` 保持 `{}`。
  而 `renderParagraphs` 裡 `if (hitMap && !(s.para_seq in hitMap)) return "";`
  —— `{}` 是 truthy，**全部句子都被濾掉** → 原文層一片空白。
  要達成註釋寫的行為，`return` 必須在 `forEach` **外面**（`if (!uids) return null;`，
  讓 `renderReader` 的 `hp` 拿到 falsy 值走全顯示分支）。
- **觸發路徑**：`hitUids` 在 `renderPerson`（`:546`）／`renderPlace`（`:635`）裡
  **無條件賦值**（哪怕是 `{}`），所以正常流程走不到。
  但 `readerState` 是**跨屏持久**的模組級變數：先看人物 A（有命中）→ 進原���層 →
  換到**沒命中的地名**（`uids = {}`）→ 開原��層 → 按「只看相關段落」→ **白屏**。
  `{}` 那條路徑是 `forEach` 正常跑完的結果，`!uids` 為 false，**連修復機制都不觸發**。
- **斷言狀態**：`pipeline/_ui_test_index.js:459` 只斷「篩選後仍有段落（篩選沒把內容全濾掉）」——
  用的是**有命中的**地名（`長安`，`hitParas` 回 `{"1":1,...}`），走不到 `{}` 路徑。
- **建議改法**：`hitParas` 開頭加 `if (!uids || !Object.keys(uids).length) return null;`，
  並讓 `renderReader` 判 `hp === null` 時走全顯示；補一條斷言：
  打開一個**該篇無命中**的作用域 → 按「只看相關段落」→ 斷段落數 > 0。
