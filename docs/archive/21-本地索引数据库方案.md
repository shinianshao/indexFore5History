## §4 第一优先：句子主键要从位置键换成稳定 uid

现在句子 id 是 `sj-001-0002-001`（书-篇-段-句序号），**这是位置键**。

一旦句子可编辑（插入 / 删除 / 合并 / 拆分），序号整体位移，会连带打垮：

- 66,782 条命中记录的 `sentence_id` 外键
- 你手写的 `overrides`（单条命中纠错）记录
- 前后快照的 diff 对比
- 静态网页的锚点

**做法**：sentence 表加一列不可变 `uid`（短哈希或 ULID），位置键降为「渲染顺序」字段。
编辑语义随之确定：

| 操作 | uid 处理 |
|---|---|
| 拆一句为二 | 前半继承原 uid，后半生成新 uid |
| 合并二句 | 保留第一句 uid，另一句标 `merged_into` |
| 删除 | 标 `dead`，不物理删（保留外键可追溯） |

**这件事必须在第一批做对**。事后补 = 所有历史数据迁移。

## §5 编辑能力分档（用户选了最深一档，这里拆成三档）

| 档 | 能改什么 | 风险 | 阶段 |
|---|---|---|---|
| a | 篇名 / 分类 / 卷次（纯元数据） | 几乎无 | P1 |
| b | 切分边界：拆句、合并、删废句 | 中，需 uid 已生效 | P4 |
| ~~c~~ | ~~直接改原文文字（校勘）~~ | ~~高：s/e 偏移全失效~~ | **不做（2026-09-26 定）** |

> **c 档已砍掉**。理由与替代方案：
> - 命中记的是字符偏移，改一个字会让同句所有命中坐标失效。
> - 真要改原文，正确做法是回去改 `data/raw` 的数据源再重跑——否则数据源一更新，
>   你在索引层的手工校勘就白改了。
> - **替代的逃生口**：允许把整句标记为 `dead`（弃用，不参与检索），
>   但不允许自由改字。这样仍能处理「这句是脏数据、别让它污染检索」的场景。

### c 档到底是什么（用一个真实例子说清楚）

句子里每条命中记的是**字符偏移**，不是文字本身。比如：

```
句子 text : 「……單于既得陵，素聞其家聲……」
命中 marks: [{"s": 12, "e": 15, "pid": "p_xxx", "tier": "core", "alias": "單于既"}]
             ↑ s/e 是「單于既」这三个字在句中的位置
```

| 档 | 你做的操作 | 后果 |
|---|---|---|
| a | 改篇名「匈奴列傳」→「匈奴列传第X」 | 只动一行元数据，命中不受影响 |
| b | 把这句拆成两句 / 和下一句合并 | 句子边界变了，但**文字没变**，靠 §4 的 uid 继承规则能兜住 |
| **c** | 把「得陵」改成「得李陵」 | **文字一变，后面所有字的位置全移**，这条命中的 `s/e` 就指错地方了，必须把该句所有命中重算 |

所以 c 的本质风险不是「能不能改」，而是**改一个字会让同句所有命中的坐标失效**。
b 档只动边界、不动字符，所以安全得多。

> 判断要不要 c 的一个经验问法：**你想改的是「这句该不该算一句」还是「这个字写错了」？**
> 前者是 b，后者是 c。后者在古籍整理里通常应该回去改 `data/raw` 的数据源，
> 而不是在索引层打补丁——否则数据源一更新，你的手工校勘就白改了。

## §5.5 Excel 工作簿怎么组织（含对「按书分 sheet」的修正）

你的提议：人名地名分开两个工作簿、每本书一个 sheet、按拼音排序。
**三条我采纳两条，中间那条要改**——因为人物是跨书实体。

### 关键问题：人物表不能按书分 sheet

劉邦在 **sj / hs / hhs / sgz / js 五本书里都有**。按书分 sheet 意味着：

- 同一个人要在 5 个 sheet 里各写一遍 → 撞车
- 你在 sj 的 sheet 里改了他的别名，hs 的 sheet 里还是旧的 → **双写漂移**

这正是 §3 红线 1 想避免的东西。人物、地名都是**全局实体**，不该按书切。

### 修正后的组织方案

| 工作簿 | sheet 划分 | 行数级 | 排序 |
|---|---|---:|---|
| `persons.xlsx` | **1 个 sheet**（加只读列 `books` 标注出现在哪几本书） | 2.3k | 拼音 |
| `places.xlsx` | **1 个 sheet**（同上） | 1.6k | 拼音 |
| `sentences.xlsx` | **按书分 sheet**；单书再超 ~3 万行就按卷拆（`sj-1` `sj-2`…） | 96k | 篇→段→句（**不按拼音**） |
| `chapters.xlsx` | 1 个 sheet | 564 | 书→卷序 |
| `overrides.xlsx` | 1 个 sheet（人工增长） | 几百 | 录入顺序 |

要点：

- **句子才按书分 sheet**——句子天然属于某一篇，不存在跨书重复问题。你说的
  「一本书多个 sheet」在这里才用得上，我按 ~3 万行一个 sheet 拆。
- **命中明细不进 Excel**（见 §6.5 容量），它只在 SQLite 和网页里看。
- **`books` 列只读**：脚本生成，给你看「這人出現在哪幾本」用，pipeline 不读它，
  你改它也没用——避免又造出一个双写源。

### 「我想只看某一本书」——用筛选实现，不拆表

你的原话：按书切 sheet 是为了「万一需要单看某本书里的内容」。
**这是「按书看」的需求，不是「按书存」的需求。** 两者要分开：

| | 按书存（拆 sheet） | 按书看（筛选） |
|---|---|---|
| 人物表 | ❌ 劉邦要写 5 遍，改一处漏四处 | ✅ 一行一个人，加 5 个布尔列筛一下 |

**实现**：人物/地名表加 5 个只读取值列 `in_sj` / `in_hs` / `in_hhs` / `in_sgz` / `in_js`
（`TRUE`/空）。想只看史記里的人 → 对 `in_sj` 筛 TRUE，一秒切换。
想换汉书 → 换个列筛。同一个视图随时可变，**不存在两份数据打架的问题**。

> 布尔列比「`books` 字符串列」好筛：字符串要用「包含」匹配，容易误中
> （筛 `sj` 会命中含该子串的其它值），而 TRUE/空是直接筛选。

如果哪天你**真想要一个物理上独立的「史記人物.xlsx」文件**，用一个只读导出脚本
随用随生成即可——它是视图，不是权威源，随便扔，不影响主表。

### 按拼音排序

- 加一列 `pinyin`（脚本用 `pypinyin` 生成，**只读辅助列**）。
  你按它排序即可；pipeline 读表不看行序，所以排序纯粹是给你看的。
- 已知坑：多音字（單于 chán yú / 单 shàn）、生僻字缺音。`pypinyin` 默认读音
  个别不准。**`pinyin` 列你随便改，不影响任何功能**。
- 句子表**不按拼音**，保持「篇→段→句」的原文顺序，否则切分编辑会错乱。

### 一句话总结 Excel 组织

| 你想要的 | 做法 |
|---|---|
| 人名、地名分开 | 两个工作簿 ✓ |
| 按拼音排序 | 加只读 `pinyin` 列 ✓ |
| 只看某本书的内容 | 布尔列 `in_sj…in_js` 筛选 ✓（不拆表） |
| 句子太长一个 sheet 装不下 | 句子表按书/卷拆 sheet ✓ |

| 表 | 关键列 | 行数级 |
|---|---|---|
| books | id, name, 卷数 | 5 |
| chapters | id, book_id, title, fullTitle, category, volume | 564 |
| sentences | uid(PK), id(位置键), chapter_id, text, paraSeq, seq, status | 96k |
| persons | id, tradName, name, dynasty, title, summary, status | 2.3k |
| aliases | person_id, alias, trad, source, note | 6k+ |
| mentions | uid, sentence_uid, person_id, surface, s, e, tier, source | 67k |
| places | id, tradName, kind, era | 1.6k |
| overrides | sentence_uid, s, e, old_pid, new_pid, note, author | 人工增长 |

索引：mentions(person_id)、mentions(tier)、sentences(chapter_id)；
`sentences(text)` 建 **FTS5**（jit 分词用 `unicode61`，古文建议再叠一个 bigram 表）。

**为什么仍要 SQLite，不全压 Excel**：
命中明细 6.7 万行装得进 xlsx（上限 104 万），筛选也能用；
但**全文检索**和**多表关联**在 Excel 里只能靠冗余宽表硬扛，几万行以上就卡。
分工是：**你只见 Excel 和一个网页，SQLite 在你的视线之外。**

## §7.5 网页两种做法的优劣

| | **A. FastAPI（+ 薄前端）** | **B. 静态预生成（http.server 起目录）** |
|---|---|---|
| 全文检索 | 真 SQLite FTS5，20 万行也毫秒级 | 要么把索引预生成成 JSON（很大），要么浏览器线性扫（几万行就卡） |
| 数据量弹性 | 按需查，**涨到 20 万行无所谓** | **全量注入浏览器**：现在 32MB 已经卡，翻倍基本撑不住 |
| 能否编辑 | 天然能加写接口（P3/P4 必需） | 不能写，只能看 |
| 打开方式 | 要跑一个 python 进程（`uvicorn`） | 双击 html 就能开，`file://` 也行 |
| 分享 | 对方也得有 python 环境 | 拷走整个文件夹就能用 |
| 依赖 | 多 `fastapi` + `uvicorn` | 零依赖 |
| 维护 | 多一处代码要维护 | 几乎不用维护 |

**结论：两个都做，但职责分开** —— 这也正好对应你选的第 4 项：

- **FastAPI 版 = 日常查询与编辑工具**（P2/P3/P4 都建在它上面）
- **静态版 = 发布/分享产物**，保持现有流程不变

决定性理由是你提的命中增长：**命中一旦到 15–20 万行，B 方案的全量注入这条路就死了**，
而 A 方案毫无压力。所以哪怕只为省事，也不该把日常工具建在 B 上。

## §8 回归方式升级（顺带解决「只许升不许降」的表达力问题）

现有：铁律是「每修一个坑 `verify.py` 加一条断言，基线只许升不许降」。**保留。**

新增：数据库化之后可以做**快照 diff**——每次重建自动对比上一次，输出三类：

- 新增命中（原本没标、现在标上了）
- 消失命中（原本标了、现在没标）← **最该看的一类**
- 归属变化（同一处从 A 改判给 B）

这比「断言条数增加」直观得多，也更贴合你「方便查找确认」的原始诉求。

## §9.5 容量规划：命中涨到 15–20 万行会怎样

你提的这点很关键，我实测推算了一遍。

**实测基座（2026-09-26）**：
- 主账本：48,461 句 / 66,557 命中 → **1.37 命中/句**
- 全量含裴注：96,444 句（裴注是独立账本，另记 `pmarks`，不计入主命中）
- 当前别名 6,100，人均 2.7 个别名

**增长推算**：待补的部分还很大——表字长尾、guess 池泛称、类传/附传书外漏召。
别名若从 6,100 补到 1.5–2 万，命中大致会到 **10–15 万**；
你估的 15–20 万属于**上限情形**（新增别名全是高频词才会到）。
方向上你是对的，我原来用 6.7 万做规划确实偏乐观。

**各层随增长的体感**：

| 层 | 现在（6.7 万） | 15–20 万时 |
|---|---|---|
| SQLite 查询 | <50 ms | 仍然 <200 ms（加索引） |
| SQLite 体积 | ~80 MB | ~250 MB，无压力 |
| **Excel 存命中** | 装得下但笨 | 装得下但打开卡 → **所以命中根本不进 Excel** |
| **静态全量注入** | 32 MB 已卡 | 60–80 MB，**浏览器撑不住** |
| 全量重标注 | 12 秒 | 估 20–40 秒，**仍不需要做增量** |

**结论：命中增长不改变架构方向，反而强化了它。**
它把「命中不进 Excel」「日常工具用 FastAPI」这两条从"建议"变成了"必须"。
唯一要调整的是 P2 一开始就做**按需查询**，不要走全量注入的老路。

### 12.1 先说一个判断：留接口主要是「数据模型」的事，不是前端的事

关系图和族谱听起来是前端功能，但真正决定成败的是**有没有结构化关系数据**。

### 12.2 关系数据模型（预留）

可用脚本先抽一批**候选关系**，再走已有的 AI 判定闭环（§取证→判→落→断言）确认。
这是后面做族谱时最省力的入场方式。

### 12.3 前端设计（详细）

#### 信息架构：沿用现有四层骨架

「一致」最省力的做法是**不重新发明交互**。现有 `app.js` 已经是四层：

```
选书 → 检索（列表） → 人物/地名详情 → 原文对照（reader 层）
```

新的 FastAPI 版**沿用这套骨架**，只换两样东西：数据层（JSON 全量注入 → 按需查询）
和视觉层。**你的肌肉记忆不用重建。**

#### 视觉：克制的古典（已确认不做竖排/印章/汉字数字）

| 令牌 | 值 | 取义 |
|---|---|---|
| `--bg` | `#F7F4EC` | 宣纸 |
| `--panel` | `#FFFDF7` | 面板，比底略亮 |
| `--text` | `#2B2A27` | 墨 |
| `--muted` | `#7A756B` | 淡墨（次要信息） |
| `--border` | `#DED8C8` | 版框线 |
| `--accent` | `#9E3D32` | **朱砂**（印章红），取代现有灰褐 `#a2977f` |
| `--accent-soft` | `#F5E9E6` | 朱砂浅底 |

字体：正文与书名走 `--serif`（宋体 / 思源宋体），**控件与数字走 sans**——
古籍感由正文承担，可读性由控件保证。

三个「一点就古典」的细节，成本低、不牺牲可读性：

1. **命中高亮用朱砂下划线**，不用荧光黄。古籍本来就用朱笔句读，语义天然吻合。
2. **分隔线用细双线**（上 1px + 下 0.5px），取版刻边框的意思。
3. 篇名一律带 `「」`，卷次写「卷三」而非「Vol.3」。

#### 关键交互

| # | 交互 | 说明 |
|---|---|---|
| 1 | 检索 | 即时反馈；自动吃简繁与异体（走现有别名机制）；可按书限定 |
| 2 | 人物详情 | 左档案（正名/朝代/头衔/别名标签/简介）+ 右命中列表（按篇分组） |
| 3 | 原文对照 | 点命中 → reader 层展开整段，**可前后翻句**，不只给一个片段 |
| 4 | **标错入口** | 每条命中右侧一个入口 → 选「应归给谁」→ 写回 `overrides`。**P3 的核心交互** |
| 5 | 键盘 | `/` 聚焦搜索、`Esc` 返回、`j/k` 翻条目 |

#### 命中置信度必须看得见（这条我认为最重要）

现有的 `tier` 字段（core / owner / chapter / era / guess …）**现在完全没暴露给用户**，
而它恰恰是「这条命中靠不靠谱」的信息：

| tier | 含义 | 呈现 |
|---|---|---|
| `core` | 正名或别名直接命中 | 朱砂**实线**下划线 |
| `owner`/`chapter`/`related` | 靠归属/篇主/关联推定 | 朱砂实线，尾部一个淡色小标（如「篇主」） |
| **`guess`** | **纯推断，未定归属** | 朱砂**虚线**下划线 + 「？」标 |

理由：你最初的诉求是「方便查找确认」——**能一眼看出哪些是硬命中、哪些是猜的**，
比多给十条命中更有价值。虚线 vs 实线是零成本的视觉编码，但省掉大量逐条核对。

（顺带：现在 guess 池 1146 处，如果都以实线呈现，你会以为它们都是确定的。）

| `rel_type` | `rel` 取值 | 说明 |
|---|---|---|

### 12.4.1 三项的落地细则（此前只记了结论，这里补设计）

**第 2 项：证据句「可有可无」怎么落地**

允许 `evidence_uid` 为空，但必须付出代价，否则无证据的关系会淹没有证据的：

| 情形 | `source` | `confidence` 上限 | 图上呈现 |
|---|---|---|---|
| 有证据句 | `manual` / `ai` | 1.0 | 实线 + 朱砂 |
| 从简介推断 | `auto-summary` | 0.6 | 虚线 |
| 纯常识推断 | `manual-guess` | 0.4 | 虚线 + 浅色 |

再给两个开关：**「只看带证据的」筛选**（默认关），以及导出时可按 confidence 阈值过滤。
这样「可有可无」不会退化成「全都是猜的」。

**第 5 项：可跨朝代，但要给密度控制**

跨朝代是默认值（不切分），因为师承、追述这类关系本来就越朝代。
但 2276 个节点跨朝代一锅炖会看不清，所以**用四个旋钮控密度**，而非切分：

1. **度数**：一度 / 二度 / 三度邻居（默认一度）
2. **关系类型**：只看 kinship（族谱）/ 只看 political / 全开
3. **朝代**：可叠加过滤（想看东汉就勾东汉）
4. **书**：按书过滤（只看某本书里出现过的关系）

跨朝代的边额外加一个**浅色渐变**标记，一眼能看出「这两个人不是一个时代的」。

### 12.5 关于「能不能做成知识图谱那种形式」

**能，而且我们的数据模型天然就是图谱**——`persons` 是节点、`relations` 是边，
这就是知识图谱的标准形态（实体—关系—属性）。真正要设计的是**怎么看**，不是能不能。

**但有一个必须提前说的陷阱**：2276 个节点如果一次性全画出来，
力导向布局会渲染成一团毛线，信息量为零。所以「知识图谱」的正确做法是：

| 视图 | 做法 | 用途 |
|---|---|---|
| **局部探索**（默认） | 从某人出发，展开一度 / 二度邻居，可切换度数 | 查「這人跟誰有關」 |
| **过滤式全局** | 按朝代 / 按书 / 按关系类型过滤后再画 | 查「東漢的婚姻網絡」这类命题 |
| **族谱树** | 只取 `kinship` 边，用树形布局（同一人可出现在多处） | 看家系 |
| 全图 | **不建议默认开启**，只作为调试视图 | — |

技术选型（都不难换，先定接口不定实现）：

- 数据：SQLite 邻接表足够；多跳查询用递归 CTE，或导出到 `networkx` 做分析
- 前端：`ECharts graph` 上手最快 / `D3 force` 最灵活 / `vis-network` 交互最省事
- 接口：前端只依赖 `renderGraph(adjacency, options)`，换库不动上层

**工作量影响**：比只做族谱多约 **300–500 行**（图控件 + 度数/过滤交互），
真正的成本不在代码，而在**关系数据本身的抽取与校验**（第 1 项要政治+社会关系，
这部分大半要靠 AI 判定闭环逐条过）。

## §13 遗留待定：断句的第二类引号问题

用户连续两次反馈「第二个引号放到后面那句去」，值得说清楚这里其实是**两件事**。

### 第一类（已修，2026-09-26）

闭引号**跑到下一句开头**：`……堯曰：「吁！凶頑，不用。」` 被切成
`……堯曰：「吁！` + `凶頑，不用。」`——等等，实际错法是 `……。` + `」……`。

修复：句末标点后连续吃掉闭合符号。**实测 7,259 句 → 0 句**，已加断言（106/106）。

### 第二类（未修，需要你定）

**开引号在上一句、闭引号在下一句**（跨句对话）。实测：

| 指标 | 数量 |
|---|---:|
| 句内「多于」（开引号跨句而去） | 4,850 |
| 句内 」多于「（承接上一句的「） | 2,242 |

典型样子：

```
句1  堯曰：「吁！
句2  凶頑，不用。」
```

**这多半是古籍的本来面目**——一段对话里有多处 `。！？`，按句读断就会把一对引号拆到两句。
它不一定是 bug，但**观感上确实像「引号没配对」**。

两个选项，我不替你决定：

| | 做法 | 代价 |
|---|---|---|
| **A 保持现状** | 尊重原文句读，跨句引号是正常现象 | 单句看引号不配对，观感不佳 |
| **B 合并跨句对话** | 开引号未闭合就一直延伸到闭引号出现，整段对话算一句 | 句子变长（可能几十字），命中偏移与阅读节奏都要重来；且一句内可能塞进多个人的发言 |

**我的倾向是 A**，理由：B 会让句子粒度失控，而这个项目的价值恰恰在「句」这层——
人物命中、关系证据句都挂在句子上。为了引号美观牺牲句子粒度不划算。
但如果你在阅读时确实被这个观感困扰，可以在**显示层**做处理
（同段对话在 reader 里连续展示、引号不配对处给个淡淡的续接标记），
**不动数据层**——这是我对 A 的改良版建议。

1. 图控件三个候选（ECharts / D3 / vis-network）你有没有偏好？
   我建议 **ECharts**——中文文档全、内置力导向，开发量最小。
2. 「无证据的关系」要不要在图上**视觉弱化**（虚线 / 浅色）？
   我建议要——这样一眼能看出哪些是硬证据、哪些是推断。
