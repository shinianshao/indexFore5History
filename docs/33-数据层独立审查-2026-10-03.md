## 一、結論

**可以合併，但有三條必須先修。**

本項目的斷言體系比我預期的紮實得多。`pipeline/verify.py` 113 條、`verify_p3.py` 164 條裡，
絕大多數是真的會變紅的——我逐條注入驗證過，不是讀代碼猜的。特別值得稱讚的是三件事：
`relations.py check` 的五個 bad 判據我全部打中過；`overrides` 的 `nth`/`s`/`e` 定位邏輯
（含 `17.0` 歸一）是真的在跑；`ERA_ORDER` 沒有第二份副本。

但有**一個真P0**：權威源 `workbook/sentences-sj.xlsx` 裡固化下來的 uid，用的是**另一套算法**，
和線上四處實現全部不一致。這不是「可能出問題」，是已經存在的、100% 不一致的狀態。
一旦有人照這張表去`overrides.xlsx` 寫錨點，會靜默失效。

另有兩條 P1 都是同一個病根：**「約定寫在文檔裡，沒有任何東西在盯著它」**——
`ERA_ORDER`/`BOOK_ERA` 的下標耦合、`tag_uids` 與 `build.py` 的算法同步，都是「改一處不會讓別處報錯」。

一個我原本以為是 P0、查完後**撤回**的懷疑：管線主鏈路（`build_dict` / `build_places` / `annotate*`）
確實只讀 xlsx，寫 xlsx 的是獨立的編輯工具，且 `build_workbook.py` 有「人工改動閘門」。
這條紅線的**意圖**是落實的，只是閘門的判據口徑有缺陷（見 P2-1）。

## 二、問題清單

### P0-1｜`sentences-sj.xlsx` 的 uid 與線上四處實現全部不一致（已存在的數據錯誤）

**位置**：`pipeline/build_workbook.py:137-140`（`make_uid`）、`pipeline/build_workbook.py:158`（調用點）
**對照**：`pipeline/common.py:343-355`（`stable_uid`）

**症狀**

`workbook/sentences-sj.xlsx` 裡 `句子` sheet 固化下來的 uid，與 `stable_uid` **逐行全不一致**。
我抽 199 行實測：

```
uid == stable_uid(篇|段|句)       : 0 行
uid == md5(篇|段|句|原文) 舊算法  : 199 行
```

**根因**

`build_workbook.make_uid` 是**五參數**（含 `text`）的舊算法：

```python
# build_workbook.py:137
def make_uid(chapter_id, para, seq, text):
    raw = "{}|{}|{}|{}".format(chapter_id, para, seq, text)   # ← 多了一段 text
    return hashlib.md5(raw.encode("utf-8")).hexdigest()[:12]
```

而線上四處（`common.stable_uid` / `app/tools/build_index_db.make_uid` /
`app/tools/overrides.py:316 uid_of` / `app/tools/verify_p3.py:163 _uid_of`）都是**三參數**。
`build_workbook.py:16` 自己的docstring 也承认「現在這版是『初版 uid』」——
但它仍然在 `sheet_sentences()`（第 158 行）裡被拿來寫出權威源表。

**為什麼是 P0**

這張表是**人寫的權威源**，`overrides.xlsx` 的錨點就是 `uid`。
人若從這張表抄一句 uid 去寫 override，該 override **永遠匹配不上**——
`overrides.py:314` 的注釋寫著「與 build_index_db 同源」，但實際不同源。
`overrides.xlsx` 目前有 0 行，所以還沒有人踩到；這正是要趁早修的理由。

**最小復現**

```python
import openpyxl, hashlib
wb = openpyxl.load_workbook("workbook/sentences-sj.xlsx", read_only=True, data_only=True)
rows = list(wb["句子"].iter_rows(values_only=True))
hdr = list(rows[0])
r = rows[1]
iu, ic, iq, isq, it = (hdr.index(x) for x in ("uid","篇(chapterId)","段序","句序","原文"))
old = hashlib.md5("{}|{}|{}|{}".format(r[ic],r[iq],r[isq],r[it] or "").encode()).hexdigest()[:12]
new = hashlib.md5("{}|{}|{}".format(r[ic],r[iq],r[isq]).encode()).hexdigest()[:12]
print(r[iu], old, new, r[iu] == new)   # 表里的 == old，!= new
```

**修法建議**：`build_workbook.make_uid` 刪掉 `text` 參數、統一調 `common.stable_uid`，
並重跑一次 `build_workbook.py --books sj` 重新固化該表。舊算法已無用處（`data/corpus` 全量是三參數 uid）。

### P1-1｜`ERA_ORDER` 與 `BOOK_ERA` 的下標耦合，改`ERA_ORDER` 不會讓任何斷言變紅

**位置**：`pipeline/annotate.py:187-190`（`ERA_ORDER`）、`pipeline/annotate.py:204-210`（`BOOK_ERA`）

**症狀**

`BOOK_ERA` 用**硬編碼整數下標**表達「哪本書記載哪個時代」：

```python
BOOK_ERA = {"sj": None, "hs": (8, 10), "hhs": (10, 11), "sgz": (11, 12), "js": (12, 15)}
```

而 `ERA_ORDER` 是一個**可變的字符串列表**。兩者靠位置綁定，沒有任何交叉校驗。

**注入實測（已做）**：把 `ERA_ORDER` 裡的「東周」刪掉（只動一個詞），書的語義全漂：

| 書 | 注入前 | 注入後 |
|---|---|---|
| `hs` | 秦末～新 | **西漢～東漢** |
| `hhs` | 新～東漢 | **東漢～三國** |
| `sgz` | 東漢～三國 | **三國～西晉** |
| `js` | 三國～十六國 | **西晉～十六國＋越界** |

**實際變紅條數：0**。`verify.py --check` 仍是 113/113，`check_trad.py` 仍全綠。

**根因**

`verify.py:663` 只驗`era_index()` 對四種簡繁異形字能否命中（**結構性**），
不校驗 `BOOK_ERA` 的**區間語義**。`BOOK_ERA` 的正確性完全靠註釋
（第 202-203 行「相鄰書有意重疊」）維護。

**影響**：`era` 檔是泛稱歸屬的第 ⑥ 級判定（`resolve_generic` 的倒數第二級）。
語義漂了會讓大批泛稱落到錯的人頭上，且**沒有任何報錯**。

**修法建議**：把 `BOOK_ERA` 的值從整數改成**朝代名列表**，如`"hs": ("秦末", "西漢", "新")`，
運行時經`era_index()` 解成下標。這樣 `ERA_ORDER` 一改，語義自動跟著走，越界會拋錯。

### P1-2｜`verify.py` 的「uid 算法四處一致」只覆蓋了兩處，注入`tag_uids` 零紅

**位置**：`pipeline/verify.py:188-209`（斷言本體）、`pipeline/tag_uids.py:51`（宣稱的共用地）

斷言名叫「新鏈路：uid 算法四處一致」，註釋寫著「防的是『四處算法（common/build/tag_uids/
build_index_db）改了但沒同步』」。但它實際只做一件事：


即：拿**產物裡已存的 uid** 和**`common.stable_uid` 現算的**比。
`build.py` 和 `tag_uids.py` 都是 `from common import stable_uid`（同一函數，正確），
所以本來就一致——這是對的設計。問題在`build_index_db.make_uid` 和
`overrides.py:316 uid_of` 這兩個**獨立的��印**。

**注入實測（已做）**：在 `tag_uids.py:51` 後插一行 `s["uid"] = "deadbeef0000"`。

**實際變紅條數：0**。`verify.py` 113/113、`check_trad.py` 全綠。

**根因**：`tag_uids.py` 只在**語料缺 uid 時**才跑，且寫的是 `data/corpus/*.json`；
而斷言遍歷的是 `book-data.json` 的 96,453 句。兩者當前無交集，所以注入完全不干擾。
真正的盲區是 `build_index_db.make_uid` 與 `overrides.uid_of` 這兩份**抄本**——
它們與 `common.stable_uid` 一致**只是巧合**（我逐字比對過，當前確實一致），
沒有任何東西在盯著它們。

**已驗證的一致性**（探針實測，三份抄本與源一致）：

```
common.stable_uid         與 common 一致? True
app/build_index_db.make_uid 與 common 一致? True
app/overrides.uid_of       與 common 一致? True
app/verify_p3._uid_of      與 common 一致? True
build_workbook.make_uid(4參) 與 common 一致? False← 這就是 P0-1
```

**修法建議**：(a) 讓 `verify.py` 直接 `import`並調用那幾份模組的 `make_uid`，
逐一斷言它們對同一組輸入產出相同結果（而不是只驗 `common`）；
(b) 長期把 `build_index_db.make_uid`、`overrides.uid_of` 改成 `from pipeline.common import stable_uid`。
順帶：斷語改成「五處」或「N 處（並逐一枚舉出來 print）」，避免名稱與實不符。

### P1-3｜做一次 P4 拆句，`verify.py` 的 uid 斷言必然變紅（假紅，會訓練作者忽略斷言）

**位置**：`pipeline/verify.py:188-193`vs `pipeline/apply_sentence_edits.py:179`

**症狀**

P4 拆句的設計是：前半繼承原 uid，後半生成 `md5(原uid|split|at)` 派生 uid，
且 `seq` 寫成**浮點數**（`sent.get("seq") + 0.5`）。而 `verify.py:192` 的判據是
「產物每句 uid 必須 == `stable_uid(位置)`」。

**推演實測（純計算，未動語料）**：

```
原句 uid       = 791cbeb17412
split@at=5 後半 uid = c19bf21e1d03seq=3.5
   verify.py 重算 stable_uid(sj-001,1,3.5) = 0ed3d6420ca1
   兩者相等? False  => verify.py 斷言會變紅（誤報）
```

**為什麼至今沒暴露**：`app/tools/verify_p3.py` 第 285-315 行**真的做了一次 split**
（`apply_sentence_edits.py add --action split`），但它走的是 `app/tools/rebuild.py`，
**事後從不跑 `pipeline/verify.py`**。兩套斷言是並列的、互不交叉（見 `verify_p3.py:6`的說明）。
所以這個衝突在測試設計上就不可能被抓到。

**影響**：一旦真的做一次 P4 拆句並跑 `verify.py`，會看到幾十萬條「uid 不一致」紅字。
作者的第一反應會是「這條斷言太嚴了/壞了」，而不是「我的P4 設計與斷言矛盾」——
這正是最壞的結局：一個學會被忽略的紅色。

**修法建議**：`verify.py:188-193` 應改為「uid 要麼等於 `stable_uid(位置)`，
要麼等於某個已登記的 P4 派生 uid（可由 `apply_sentence_edits` 的規則重算）」，
或在 `verify.py` 裡對 `seq` 為整數的句子才做位置重算，浮點 `seq` 走另一條判據。
另外建議 `verify_p3.py` 的 split 測試塊尾補跑一次 `pipeline/verify.py --check`。

### P1-4｜單向性斷言只盯2 個權威源，另外 4 個 xlsx 无人看管

**位置**：`app/tools/verify_p3.py:88-102`（`test_one_way`）vs `pipeline/` 裡 4 個寫xlsx 的腳本

**症狀**

`test_one_way` 的「單向性」只對兩個文件取 md5：

```python
before = (md5(PEOPLE), md5(XLSX))   # PEOPLE=people.json, XLSX=overrides.xlsx
```

但 `workbook/` 下實際有 **6 個**權威源，其中 4 個有 `pipeline/` 裡的寫入路徑：

| 權威源 | 誰會寫它 | 有沒有差異閘門 | 有沒有斷言盯著 |
|---|---|---|---|
| `overrides.xlsx` | `app/tools/overrides.py` | — | ✅ `verify_p3.test_one_way` |
| `persons.xlsx` | `pipeline/build_workbook.py` | ✅ `resolve_target` | ❌ |
| `places.xlsx` | `pipeline/build_workbook.py` | ✅ `resolve_target` | ❌ |
| `relations.xlsx` | **`pipeline/relations.py`**（`_append_row`/`_set_status`）、`pipeline/_apply_rel_evidence.py`、`pipeline/_rename_placeholder_pids.py` | ❌ **無條件覆蓋** | ❌ |
| `sentence-edits.xlsx` | `pipeline/apply_sentence_edits.py` | ❌ **無條件覆蓋** | ❌ |
| `sentences-sj.xlsx` | `pipeline/build_workbook.py` | ❌（自稱派生視圖） | ❌ |

**已實測確認的越界風險**：`relations.py:205-217` 的 `_append_row` 與
`relations.py:294-320` 的 `_set_status` 都是**直接 `wb.save(WORKBOOK)`**，
沒有 `build_workbook.resolve_target` 那样的「檢測人工改動 → 寫 `.new.xlsx`」閘門。
`apply_sentence_edits.py:111-150` 同理。

**為什麼仍評P1 而非 P0**：`relations.py` 的寫入發生在**人主動執行 `add`/`revoke` 子命令**時，
語義上等同「人自己在改權威源」，不算「pipeline 悄悄沖掉你的審定」。
`build_workbook.py` 那條路徑有閘門，是作者刻意的設計。
**但 `sentence-edits.xlsx` 有真問題**（見 P2-2），而**整個 4 個文件無斷言覆蓋**這件事本身是缺口。

**根因**：紅線1 的守門只做在了「人會大量手改的表」（persons/places/overrides）上，
沒覆蓋「以程式寫入為主、但同樣是權威源」的 relations/sentence-edits。

**修法建議**：(a) `test_one_way` 擴成遍歷 `workbook/*.xlsx` 全量取 md5；
(b) `relations.py` 與 `apply_sentence_edits.py` 的寫入加一道「只append/只改指定行，
不重排既有行」的守衛（現在 `openpyxl` 重存會改全部行的內部 XML）；
(c) 至少加一條斷言：「`relations.xlsx` 的 active 行數 == 庫裡 relations 表的行數」。

### P2-1｜`build_workbook` 閘門的 `_norm` 不做簡繁歸一，把1 條真實資料差異判成「人工改動」

**位置**：`pipeline/build_workbook.py:224-229`（`_norm`）

**症狀**

我用 `resolve_target` 的真判據（只讀，未寫任何檔案）實測 `persons.xlsx` 現狀，得到：

```
源數據人物數: 2240
新增 613  改 1  表裡有源沒有 613
  [改] p_yuantang
      表裡  ：('袁湯', '东汉', ..., '字仲河，袁京之子、袁安之孫；桓帝初為司空，封安國亭侯。', ...)
```

`p_yuantang` 那一條**只是簡繁不同**（`東漢/东汉`、`安國亭侯/安国亭侯`、`為/为`），
不是人改的。`_norm` 只做 `str(v).strip()`，不做 `t2s/to_trad` 歸一。

**影響**：目前這條誤判**僥倖地讓閘門變嚴**（判成「有人改過」→ 寫 `.new.xlsx` → 原表安全）。

**附帶發現**：`表裡有源沒有 613` 條（如 `p_luxiaowang`、`p_zhaoqingwang`…，
簡介都是「各書提及人物（A類召回），出現在 hs」）說明 **`persons.xlsx` 與
`people.json` 之間存在 613 個 pid 的實質漂移**。這是資料一致性問題，不是審查範圍內的
（屬詞典層），但值得作者注意——`build_dict.py` 只讀 xlsx，所以 xlsx 是實際權威源，
漂移意味著 people.json 與 xlsx 對不上。

**修法建議**：`_norm` 裡加`t2s()`（或 `to_trad`）歸一再比。

### P2-3｜`check_trad.py` 的 F/G 層驗的是 `web/`，而現行前端在 `app/web/`
