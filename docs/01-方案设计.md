# 古籍检索与对照小程序 — 方案设计

> 版本 v1.1 · 2026-09-20
> 首版范围：前四史（史记 / 汉书 / 后汉书 / 三国志）+ 晋书，人名索引与跨书对照
> v1.1 变更：核实云托管平台限制后调整服务端形态为单服务 + 轻量自建索引

---

## 一、需求解析

### 1.1 核心场景

用户输入「刘邦」，期望得到**分层的两类结果**：

| 结果类型 | 判定条件 | 展示内容 |
|---|---|---|
| 整篇讲述 | 该篇目的主人公是刘邦 | 仅篇名 + 链接，不列句子 |
| 顺带提及 | 该篇目主人是别人，但正文提到刘邦 | 篇名 + 链接 + 具体句子 |

再进阶：

- **跨书记载对照**：同一事件（如鸿门宴）在《史记》《汉书》中的不同记载并列展示
- **自动关联聚类**：按人物/事件把各书相关段落自动聚成一页
- **地名索引 / 时间索引**：把检索目标从人名扩展到地名与纪年
- **多古籍导入**：管线可配置，新增书籍无需改代码

### 1.2 关键技术判断

这不是一个「全文搜索」问题，而是 **实体索引 + 篇目分层** 问题。全文搜索只能给出「哪些句子含这三个字」，无法回答「这一整篇是否专讲此人」。因此必须：

1. **离线预处理**完成实体识别与篇目归主，构建结构化索引；
2. 小程序端**只查索引**，原文按需拉取，控制流量与耗时；
3. 管线与前端解耦，后续扩展到地名/时间只是换标注目标，架构不变。

## 二、系统架构

三层结构，离线与在线彻底分离：

```
公版语料源
   │
   ▼
[离线管线 · 本地 Python]  抓取清洗 → 切分标注 → 构建索引
   │  (产出 MeiliSearch 可导入的 NDJSON)
   ▼
[云托管服务 · 微信云托管]  MeiliSearch 引擎 + Node API 网关
   │  (wx.cloud.callContainer 内网调用，免配域名)
   ▼
[小程序端 · 原生开发]  搜索 → 结果分组 → 人物页 → 阅读 / 对照
```

### 2.1 为什么是「云托管 + 检索引擎」

微信原生云开发（云函数 + 云数据库）**不支持中文分词的全文索引**，只能做正则匹配，无法满足「任意关键词检索」的需求。云托管可以部署自定义容器，从而引入检索引擎：

| 对比项 | 云开发（云函数+数据库） | 云托管 + 自建检索引擎（已选） |
|---|---|---|
| 中文全文检索 | 弱（仅正则） | 强（分词、相关度排序、高亮） |
| 检索「约法三章」这类事件词 | 不支持 | 支持 |
| 部署复杂度 | 低 | 中（需 Dockerfile） |
| 费用 | 极低 | 按容器规格与时长计费 |
| 免域名配置 | 是 | 是（callContainer 走微信内网） |

### 2.2 服务端部署形态（已按平台限制调整）

核实官方文档后确认：云托管的容器**没有持久化存储**——容器恢复即回到镜像固化状态，容器内任何写操作都不保存。因此索引数据必须随镜像分发，容器内只读。

据此调整为**单个服务**：

- `api` — Node（Fastify）网关，内置轻量倒排索引；索引文件在构建阶段打进镜像，容器启动时加载进内存

检索引擎选型：

| 方案 | 冷启动 | 内存占用 | 结论 |
|---|---|---|---|
| 轻量自建索引 | 约 15-20 秒 | 约 300MB | **首版采用**，覆盖实体检索与篇目聚合 |
| MeiliSearch 容器 | 约 30-60 秒 | 1GB 以上 | 需要任意词全文检索时再引入 |

选型理由：首版是**结构化精确检索**（实体匹配 + 篇目聚合），不需要全文检索引擎；在容器无持久化的前提下引入 MeiliSearch 会显著拉长冷启动、抬高规格与成本。接口层设计保持不变，后续升级不影响小程序端。

> 详细依据见 `docs/02-账号开通与成本清单.md` 第四、五节。

## 三、离线数据管线

每一步产物落盘，可单独重跑，`config/books.yaml` 是唯一需要为新书改动的地方。

| 步骤 | 脚本 | 输入 → 输出 | 说明 |
|---|---|---|---|
| 1 抓取 | `01_fetch.py` | 语料源 → `data/raw/*.txt` | 维基文库 / ctext.org，按书分文件 |
| 2 清洗 | `02_clean.py` | raw → `data/clean/*.txt` | 去注疏夹注、统一标点、保留异体字 |
| 3 切分 | `03_segment.py` | clean → `data/corpus/chapters/*.json` | 书 → 篇 → 段 → 句，生成稳定 ID |
| 4 词典 | `04_persons.py` | 篇名 + 别名源 → `data/dict/persons.json` | 人物主名、别名、朝代、简介 |
| 5 标注 | `05_annotate.py` | corpus + dict → 带实体标注的 JSON | Aho-Corasick 多模式匹配 + 消歧 |
| 6 聚类 | `06_events.py` | 标注结果 → `data/corpus/events.json` | 事件簇（M2 启用） |
| 7 建索引 | `07_build_index.py` | 全部 → `data/index/*.ndjson` | 生成三个索引的导入文件 |

### 3.1 切分与 ID 设计

稳定 ID 是全局一切关联的基础，格式为 `书简码-卷序-段序-句序`：

```
sj-008-0012-003
│   │    │    └─ 第 3 句
│   │    └────── 第 12 段
│   └─────────── 第 8 卷（高祖本纪）
└─────────────── 史记
```

句子边界：`。！？` 为主，`；` 可切可不切（配置项）。段落边界依原文换行。

### 3.2 篇目集归主（关键简化）

史书篇名本身携带大量信息：`高祖本纪`、`淮阴侯列传`、`萧相国世家`——标题中的封号/谥号**往往就是主人物**。因此：

> 篇目主人物 = 从篇名解析 + 少量人工校正表

这比跑一遍 NER 再统计准确得多，也便宜得多。校正表放 `config/chapter_owners.yaml`，处理「五宗世家」「吕太后本纪」这类不能直接切名的标题。

## 四、索引与数据模型

### 4.1 三个索引

**`chapters` — 篇目索引**（约 400 条，五部史书全部篇目）

```json
{
  "id": "sj-008",
  "book": "史记", "bookId": "sj",
  "title": "高祖本纪", "fullTitle": "史记·高祖本纪",
  "category": "本纪", "volume": 8,
  "mainPersons": ["p_liubang"],
  "mainPlaces": ["pl_peixian"],
  "yearRange": [-256, -195],
  "summary": "记述刘邦自起兵反秦至建立汉朝、平定天下的全过程。",
  "charCount": 8600,
  "sentenceCount": 412
}
```

检索配置：`searchable` = title, fullTitle, summary；`filterable` = bookId, category, mainPersons, mainPlaces

**`sentences` — 句子索引**（约 20–30 万条，主体数据）

```json
{
  "id": "sj-008-0012-003",
  "bookId": "sj", "book": "史记",
  "chapterId": "sj-008", "chapterTitle": "高祖本纪",
  "paraSeq": 12, "seq": 3,
  "text": "沛公左司马曹无伤使人言于项羽曰：「沛公欲王关中，使子婴为相，珍宝尽有之。」",
  "persons": ["p_liubang", "p_xiangyu", "p_caowushang"],
  "places": ["pl_guanzhong"],
  "years": ["-206"],
  "isMainChapter": true,
  "eventId": "ev_hongmenyan"
}
```

检索配置：`searchable` = text；`filterable` = bookId, chapterId, persons, places, years, eventId

**`persons` — 人物索引**（约 3000–5000 条）

```json
{
  "id": "p_liubang",
  "name": "刘邦",
  "aliases": ["高祖", "汉高祖", "沛公", "汉王", "刘季", "季"],
  "dynasty": "西汉",
  "title": "汉太祖高皇帝",
  "summary": "沛郡丰邑人，西汉开国皇帝。",
  "chapterCount": 2,
  "mentionCount": 1580,
  "relatedPersons": ["p_xiangyu", "p_zhangliang", "p_hanxin"]
}
```

### 4.2 数据量估算

| 书 | 字数 | 预计句数 |
|---|---|---|
| 史记 | ~52 万 | ~4.0 万 |
| 汉书 | ~75 万 | ~5.8 万 |
| 后汉书 | ~90 万 | ~7.0 万 |
| 三国志 | ~35 万 | ~2.7 万 |
| 晋书 | ~100 万 | ~7.7 万 |
| 合计 | ~352 万 | ~27 万 |

索引体积预估 50–120 MB（含原文），MeiliSearch 单实例完全可承载。

## 五、服务端 API

| 接口 | 用途 | 关键参数 |
|---|---|---|
| `GET /api/search` | 统一检索入口 | `q`（关键词）, `mode=person\|place\|time\|fulltext`, `book` |
| `GET /api/person/:id` | 人物详情 | 返回人物卡 + 主篇目 + 提及篇目（含句） |
| `GET /api/chapter/:id` | 篇目元信息 | 标题、卷次、字数、包含人物 |
| `GET /api/chapter/:id/content` | 篇目全文 | 分页或分段返回，避免超包 |
| `GET /api/compare` | 跨书对照 | `eventId` 或 `entityId`，多书并列 |
| `GET /api/books` | 书目列表 | 五部史书的卷数、篇数、字数 |
| `GET /api/suggest` | 输入联想 | 人物名/别名前缀匹配 |

### 5.1 `/api/search` 聚合逻辑（查「刘邦」的完整链路）

```
1. 别名归一：刘邦 / 高祖 / 沛公 / 汉王 → p_liubang
2. 查 chapters：filter=mainPersons:p_liubang
   → 主篇目：史记·高祖本纪、汉书·高帝纪上、汉书·高帝纪下
3. 查 sentences：filter=persons:p_liubang，按 chapterId 分组统计
   → 提及篇目：史记·项羽本纪（3 处）、史记·萧相国世家（2 处）...
4. 从「提及篇目」中剔除已在「主篇目」中的项（避免重复）
5. 若命中 eventId 聚类，附上对照候选
6. 输出结构化 JSON，前端直接渲染
```

返回结构：

```json
{
  "query": "刘邦",
  "normalized": { "type": "person", "id": "p_liubang", "name": "刘邦" },
  "primary":  [ { "chapterId": "sj-008", "fullTitle": "史记·高祖本纪", "charCount": 8600 } ],
  "mentions": [
    {
      "chapterId": "sj-007", "fullTitle": "史记·项羽本纪",
      "count": 3,
      "sentences": [
        { "id": "sj-007-0021-005", "text": "...", "highlight": "沛公" }
      ]
    }
  ],
  "total": { "primary": 3, "mentionChapters": 47, "mentionSentences": 1580 }
}
```

### 5.2 性能要点

- 接口只返回**必要字段**，句子按篇目分页（每篇首屏 3 句，展开再拉）
- 服务端缓存高频人物（如刘邦、项羽）的聚合结果，TTL 1 小时
- 全文正文与索引分离，`/content` 走云存储直链或独立接口
- 响应体控制在 256 KB 以内（小程序 setData 上限约束）

## 六、小程序端设计

### 6.1 页面清单与分包

```
主包（首页 + tabBar 必须）
├── pages/index/index      首页：搜索框、五部史书入口、热门人物
├── pages/search/search    搜索结果页（核心页面）
├── pages/person/person    人物详情页
└── pages/mine/mine        关于、数据说明、反馈

分包 packageRead（阅读与对照）
├── chapter/chapter        篇目阅读（原文，人名高亮可点）
└── compare/compare        跨书对照页

分包 packageIndex（M3 启用）
├── place/place            地名索引
└── timeline/timeline      时间索引
```

主包仅放四个高频页面，阅读与对照进分包并用 `preloadRule` 预下载。

### 6.2 结果页核心交互

```
┌─────────────────────────────┐
│ [刘邦]                       │  ← 搜索框，带别名提示
├─────────────────────────────┤
│ 整篇讲述（3）                 │  ← 分组一
│  《史记·高祖本纪》        8.6千字 │
│  《汉书·高帝纪上》        5.2千字 │
│  《汉书·高帝纪下》        4.8千字 │
├─────────────────────────────┤
│ 其他篇目提及（47 篇 / 1580 处）  │  ← 分组二，可折叠
│  《史记·项羽本纪》         3 处 │
│    · 沛公左司马曹无伤使人言于项羽曰…│
│    · 沛公旦日从百余骑来见项王…    │
│  《史记·萧相国世家》        2 处 │
│    · 高祖为布衣时，何数以吏事护高祖。│
└─────────────────────────────┘
```

设计要点：

- 命中词在句中**高亮**，且高亮的是**真实出现的别名**（显示「沛公」，不是「刘邦」）——这点对古籍检索体验至关重要
- 提及分组按篇目聚合，默认每篇展示 3 句，点击篇名进入阅读页定位
- 顶部提供筛选：按书目筛选、只看本纪/列传

### 6.3 阅读页

- 原文竖排可用普通横排（首版横排，降低实现成本）
- 人名/地名以浅色下划线标记，点击跳转对应实体页
- 支持「从结果跳入并定位到句」，目标句高亮背景色
- 长文本分段懒加载，避免一次性 setData 过大

## 七、难点与对策

### 7.1 别名归一（最高优先级）

**古籍中「刘邦」二字几乎不出现**，实际用「高祖」「沛公」「汉王」「刘季」。不做别名表，检索结果基本为空。这是整个项目成败的关键点。

对策：

1. 从篇名解析出主名（淮阴侯列传 → 韩信）；
2. 用大模型辅助生成别名候选，人工审核后入表；
3. 别名冲突检测：「韩信」与「韩王信」是两个人，「沛公」既是刘邦也是地名相关词；
4. 单字别名（如「季」）不单独入索引，容易误命中。

### 7.2 同名歧义

- 同书不同人同名：需按篇目上下文消歧（出现在谁的传记里，倾向指谁）
- 单名 vs 全名：「信」可能指韩信、韩王信、陈信
- 对策：首版**只索引长度 ≥2 的别名**，消歧用「篇目主人优先」规则兜底

### 7.3 事件聚类（M2）

跨书对照的核心。同一事件在不同书中的记载：

- 强特征事件（鸿门宴、垓下之战）可先用「共同人物 + 相近年代 + 相同地名」做候选簇，再用大模型打事件标签
- 成本控制：只对共享实体的句子集合做聚类，不做全量
- 人工审核事件名，沉淀成 `data/dict/events.json`，可复用

### 7.4 文本质量

- 语料源需选**公版或 CC 授权**文本，避免使用现代点校本
- 异体字、通假字保留原样，检索时做繁简/异体归一并查
- 标注残留的注疏文字需在清洗阶段剔除

## 九、风险与合规

| 风险 | 说明 | 对策 |
|---|---|---|
| 语料版权 | 公版原文可自由使用，现代点校本有整理者版权 | 仅取维基文库 / ctext.org 等公版或 CC 源 |
| 云托管成本 | 按容器规格与运行时长计费 | 选用最小规格，索引构建在本地完成，云端只读 |
| 类目与审核 | 古籍查询类小程序需选对服务类目 | 建议「工具-信息查询」或「教育-在线阅读」，需核实最新类目要求 |
| 内容合规 | 纯公版古籍、无 UGC，风险低 | 首版不开放用户上传与评论 |
| 检索准确度 | 别名覆盖不全导致漏检 | 首版可接受不完整，持续补别名表；提供「反馈漏检」入口 |

## 十、已确认的决策

| 事项 | 结论 |
|---|---|
| 人名覆盖策略 | 首版**只覆盖有传记的人物**（约 800-1000 人），准确率优先，后续再扩 |
| 语料源 | **维基文库优先**，ctext.org 作补充 |
| 账号与云资源 | 均未开通，按 `docs/02-账号开通与成本清单.md` 申请；开发不依赖云资源，可先行 |
| 检索实现 | 首版用**轻量自建索引**，MeiliSearch 作为后续升级项 |
| 服务端形态 | 单个云托管服务，索引随镜像分发，容器内只读 |
