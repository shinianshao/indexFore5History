## 〇、一句话结论

**管线验收门是绿的，但产品体验与词典完备度并未同步达标。**  
问题不在「算法三层」（切分/标注/守卫骨架已稳），而在：

1. **前端书作用域状态机**有明确逻辑错误（多书合检灯、裴注开关语义）；
2. **后汉书/三国志词典仍是「速补 + 主路径」**，字、尊称、附传人物大量欠账（史记主路径早期手工补过，对照之下落差被放大）；
3. **裴注是独立索引**，与正文统计脱节——用户感知「点了没用」在产品语义上成立；
4. **少数关键人物（司马懿家族等）命中被泛称/漏召吃掉**，属于正确性事故，不是体验瑕疵。

## 二、前端：选书 / 多书合检 / 裴注（用户直接撞到的）

### 2.1 「默认全选，但多书合检不亮」——确定是 bug

**位置**：`web/app.js` `renderBookBar()`

```js
var allOn = scope.length === BOOKS.length && !peiOn;
```

**实况**：

- 初始化 `scope = 全部书`，`peiOn = true`（默认开裴注）；
- 于是 `scope.length === BOOKS.length` 为真，但 `!peiOn` 为假 → **allOn = false**；
- 界面四本都亮着，右侧「多书合检」却是灭的。

**连带**：点「多书合检」会执行 `peiOn = false`——把「合检」和「关裴注」绑死了。用户语义上「合检」= 多书同时检索，与裴注无关。

**修法建议**：

1. `allOn` 改为 `scope.length === BOOKS.length`（是否合检只看书集合）；
2. 「多书合检」点击 = 全选书；**不要**顺手关裴注；
3. 裴注仅是三国志附属层，单独记忆开/关。

### 2.2 「点不点裴注，后面的统计都一样」——半设计、半产品缺陷

**设计如此**（`docs/10` 已拍板：裴注「保留为注，不参与统计」）：

- `scopeStat` / `mentionCount` / 索引排序 / 稱謂 ×N **全部只扫正文 `sentences`**；
- 裴注走 `window.PEI_DATA`，在人物页**另开一行/一组**（`peiBlock` / `peiSection`）。

所以：

| 用户预期 | 现状 |
|---|---|
| 开裴注后，提及总数、称谓次数、索引排序应变大 | **不变**（注文永不进正文账） |
| 关掉裴注应隐藏注文 | **会隐藏**（这部分是对的） |
| 开关应有可见差别 | 仅人物页底部多一块；索引页/快捷词/排序**完全无感** |

**产品层问题**（即使坚持「注不进正文统计」也应修）：

1. 裴注开关对**索引列表、检索候选、快捷词**零影响——看起来像坏的；
2. 人物页「其他篇目提及 N 处」旁的裴注行是附加行，用户容易当成同一组统计里的开关；
3. `inScope()` 对 `sgz-*` 有一条特判：`peiOn` 时**无条件放行全部三国志章节**，与 `scope` 书集合脱钩，状态机不干净。

**修法建议**（二选一，需产品拍板）：

- **A（推荐，保持统计纯净）**：裴注开关影响面扩大到「人物页可见性 + 索引旁灰字角标（裴注 N）」；主统计仍不进；UI 文案写清「注文不计入提及总数」。
- **B（用户直觉）**：开裴注时提供「含注」合计列（正文 N + 注文 M），关则只显示 N；排序可选是否含注。主 `mentionCount` 字段仍不回写，避免断言爆炸。

### 2.3 状态机其它毛刺

| 现象 | 根因 |
|---|---|
| 默认 `peiOn=true`，与「多书合检」灯互斥 | §2.1 公式 |
| 取消三国志会强制 `peiOn=false`，再选回三国志**不会**自动开裴注 | 只写了单向联动 |
| 注释写「三国志在作用域时自动开」 | 实际只在**点裴注胶囊**时自动补选 sgz，初始化/勾选 sgz 都不会自动开 |
